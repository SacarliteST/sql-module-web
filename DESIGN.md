# DESIGN.md - контур преподавателя

Документ нужен как самодостаточное задание для нейронки/агента, который будет проектировать или реализовывать контур преподавателя в `sql-module-web`.

## Контекст проекта

`sql-module-web` - фронтенд SQL-модуля для образовательной системы тестирования. Сейчас приложение развивается как standalone SPA, но архитектурно должно быть готово к будущему встраиванию в родительскую систему.

Стек проекта:

- React + TypeScript + Vite;
- Mantine UI;
- React Router;
- TanStack Query;
- Zustand;
- React Hook Form + Zod;
- Orval для генерации API-клиентов;
- Monaco Editor для SQL-редактора;
- React Flow в будущем для визуального конструктора схемы.

Роли приложения:

- `Admin` - отдельная заглушка/служебный контур;
- `Teacher` - подготовка SQL-материалов;
- `Student` - решение SQL-заданий.

Этот документ описывает именно `Teacher` contour.

## Главная цель контура преподавателя

Дать преподавателю рабочий интерфейс для подготовки учебных SQL-материалов:

1. Настроить каталог СУБД и физических типов.
2. Создать учебную базу данных (`TargetDb`).
3. Описать схему: таблицы, атрибуты, связи.
4. Наполнить базу тестовыми данными.
5. Создать темы.
6. Создать эталонные SQL-запросы.
7. Создать задания, привязанные к теме и эталонному запросу.
8. В будущем смотреть попытки студентов.

Базовый workflow:

```text
Каталог СУБД -> Учебная БД -> Схема -> Данные -> Темы -> Эталонные запросы -> Задания -> Попытки
```

## Правила разработки

Обязательно:

- использовать Mantine, не подключать Bootstrap;
- соблюдать стиль из `docs/testing-system-ui-style.md`;
- использовать существующие общие компоненты из `src/shared/ui`;
- не редактировать вручную файлы в `src/api/identity` и `src/api/sqlmodule`;
- не хардкодить адреса API в компонентах;
- брать адреса из `public/runtime-config.json` и существующего HTTP-слоя;
- держать задачи маленькими итерациями;
- после кодовых изменений запускать `npm run typecheck` и `npm run build`;
- если агент поднимал dev-сервер для проверки, после проверки обязательно остановить его.

Запрещено без отдельного согласования:

- добавлять новый UI-kit;
- делать глобальный редизайн всего приложения;
- переписывать текущую авторизацию;
- менять сгенерированные Orval-клиенты вручную;
- делать весь контур преподавателя одной огромной задачей;
- добавлять новые зависимости без явной необходимости.

## Архитектура

Использовать Feature-Sliced-lite без фанатичного дробления:

```text
src/
  app/              # router, layout, providers, runtime config
  pages/            # страницы верхнего уровня
  features/         # пользовательские сценарии
  entities/         # доменные сущности
  shared/           # общие UI, helpers, http, types
```

Для контура преподавателя предпочтительное направление:

```text
src/
  pages/
    teacher-home/
    teacher-dbms/
    teacher-schemas/
    teacher-topics/
    teacher-sql-queries/
    teacher-tasks/

  features/
    dbms-catalog/
    schema-editor/
    training-content/

  entities/
    dbms/
    schema/
    topic/
    sql-query/
    sql-task/
```

Если текущая итерация маленькая, не нужно сразу создавать все папки. Структуру наращивать по мере появления реальной логики.

## Общий стиль UI

Интерфейс должен ощущаться как спокойный рабочий инструмент для преподавателя, а не как landing page.

Визуальное направление:

- темная верхняя шапка;
- светлый нейтральный фон рабочей области;
- компактные страницы;
- обычные заголовки уровня `h2/h3`, без hero-блоков;
- хлебные крошки на вложенных страницах;
- карточки с тонкой рамкой и небольшим радиусом;
- плотные таблицы с границами и hover-состоянием;
- синие primary-действия;
- серые secondary-действия;
- красные destructive-действия;
- создание/редактирование/удаление через модальные окна;
- пустые состояния простым текстом, без декоративных иллюстраций.

Mantine-перевод:

- `Button`, `Group`, `Stack`, `Grid`, `SimpleGrid`;
- `Card`/существующий `AppCard`;
- `Table`;
- `Modal`;
- `TextInput`, `Textarea`, `Select`, `NumberInput`, `Checkbox`;
- `Tabs` для сложных редакторов;
- `Breadcrumbs` или существующий `PageBreadcrumbs`.

## Уже существующие общие компоненты

Перед созданием нового UI-паттерна проверить `src/shared/ui`.

Сейчас есть:

- `Page`;
- `PageHeader`;
- `PageBreadcrumbs`;
- `AppCard`;
- `EmptyState`;

## Основные сущности преподавателя

### Каталог СУБД

Сущности:

- `DbmsDictionary`;
- `PhysicalType`;
- `ParameterDefinition`.

Назначение:

- преподаватель или администратор модуля видит доступные СУБД;
- настраивает физические типы;
- настраивает параметры атрибутов.

Страница должна быть табличной, с CRUD через модалки.

### Учебные базы и схемы

Сущности:

- `TargetDb`;
- `MetaTable`;
- `MetaAttribute`;
- `MetaRelationship`;
- `AttributeParameterValue`;
- `CreateSchemaRequest`;
- `CreateSchemaResponse`.

Назначение:

- создать учебную БД;
- выбрать СУБД;
- описать таблицы, колонки и связи;
- валидировать/создать физическую схему.

Первая итерация может быть простой табличной/формовой. React Flow подключать отдельной задачей, когда будет понятна структура данных и DTO.

### Данные

Сущности:

- `DataRecord`;
- `CellValue`.

Назначение:

- заполнить таблицы учебной БД тестовыми данными;
- дать студентам воспроизводимую среду для `SELECT`-запросов.

В первой итерации допустимы простые таблицы и формы. Сложный spreadsheet-like редактор - отдельная будущая задача.

### Темы

Сущность:

- `Topic`.

Назначение:

- сгруппировать задания по темам;
- поддержать иерархию тем;
- дать основу для будущего ограничения видимости материалов.

UI:

- дерево тем;
- кнопки создания, редактирования, удаления;
- перемещение темы отдельной задачей, если API поддерживает `MoveTopicRequest`.

### Эталонные запросы

Сущность:

- `SqlQuery`.

Назначение:

- преподаватель выбирает учебную БД;
- пишет эталонный SQL-запрос;
- backend исполняет/хранит результат как эталон для проверки студента.

UI:

- список эталонных запросов;
- форма создания/редактирования;
- поле SQL в будущем на Monaco Editor;
- в первой итерации можно использовать `Textarea`, если задача не про редактор.

### Задания

Сущность:

- `SqlTask`.

Назначение:

- связать тему, учебную БД через эталонный запрос и текст задания;
- задать название, описание/условие, сложность;
- подготовить материал для студента.

UI:

- таблица заданий;
- фильтры по теме и базе;
- форма создания/редактирования;
- быстрый переход к эталонному запросу.

### Попытки студентов

Сущности:

- `Attempt`;
- `SubmitAttemptResponse`.

Назначение:

- мониторинг решений студентов;
- просмотр статуса, ошибок и результата проверки.

Это не первый приоритет. Достаточно оставить пункт в навигации как будущий раздел или заглушку.

## API-ориентиры

Сгенерированные клиенты находятся здесь:

- `src/api/sqlmodule/dbms-catalog/dbms-catalog.ts`;
- `src/api/sqlmodule/schema/schema.ts`;
- `src/api/sqlmodule/training/training.ts`;
- `src/api/sqlmodule/model/*`.

Перед использованием конкретного hook обязательно проверить его точное имя в сгенерированном файле.

Ожидаемые группы hook:

- `useGetAllDbmsDictionaries`, `useCreateDbmsDictionary`, `useUpdateDbmsDictionary`, `useDeleteDbmsDictionary`;
- `useGetAllPhysicalTypes`, `useCreatePhysicalType`, `useUpdatePhysicalType`, `useDeletePhysicalType`;
- `useGetAllParameterDefinitions`, `useCreateParameterDefinition`, `useUpdateParameterDefinition`, `useDeleteParameterDefinition`;
- `useGetAllTargetDbs`, `useCreateTargetDb`, `useUpdateTargetDb`, `useDeleteTargetDb`;
- `useGetAllMetaTables`, `useGetAllMetaAttributes`, `useGetAllMetaRelationships`;
- `useGetAllDataRecords`, `useGetAllCellValues`;
- `useGetAllTopics`, `useCreateTopic`, `useUpdateTopic`, `useDeleteTopic`;
- `useGetAllSqlQueries`, `useCreateSqlQuery`, `useUpdateSqlQuery`, `useDeleteSqlQuery`;
- `useGetAllSqlTasks`, `useCreateSqlTask`, `useUpdateSqlTask`, `useDeleteSqlTask`;
- `useGetAllAttempts`.

Если hook отсутствует или называется иначе, использовать фактическое имя из Orval-клиента, а не придумывать новое.

## Предлагаемая навигация преподавателя

Маршруты можно вводить постепенно:

```text
/teacher
/teacher/dbms
/teacher/schemas
/teacher/schemas/:targetDbId
/teacher/topics
/teacher/sql-queries
/teacher/tasks
/teacher/attempts
```

`/teacher` - стартовая страница преподавателя.

На стартовой странице должны быть компактные блоки-переходы:

- "Каталог СУБД";
- "Учебные базы";
- "Темы";
- "Эталонные запросы";
- "Задания";
- "Попытки студентов" как будущий раздел.

Каждый блок:

- короткий заголовок;
- одно предложение о назначении;
- кнопка перехода;
- при наличии данных можно показать счетчик.

## Первая разумная итерация

Не нужно сразу делать весь контур преподавателя.

Первая итерация должна дать аккуратный каркас:

1. Обновить `TeacherHomePage`.
2. Сделать страницу похожей на рабочий dashboard.
3. Добавить карточки основных разделов.
4. Не делать настоящие CRUD-формы.
5. Не подключать Monaco и React Flow.
6. Не менять backend/API.
7. Оставить все будущие разделы в виде понятных переходов или заглушек.

Definition of Done первой итерации:

- после логина под `Teacher` открывается `/teacher`;
- страница визуально соответствует стилю проекта;
- есть понятные разделы будущего контура;
- нет декоративного landing page;
- `npm run typecheck` проходит;
- `npm run build` проходит.

## Следующие итерации

Рекомендуемый порядок:

1. Dashboard преподавателя.
2. Каталог СУБД: список + create/edit/delete.
3. Учебные базы: список `TargetDb` + создание.
4. Простое отображение схемы выбранной базы.
5. Темы: дерево + CRUD.
6. Эталонные запросы: список + форма.
7. Задания: список + форма.
8. Данные учебной базы.
9. React Flow schema constructor.
10. Monaco для SQL-запросов.
11. Мониторинг попыток.

Каждый пункт делать отдельным маленьким промтом/итерацией.

## Требования к экрану TeacherHomePage

`TeacherHomePage` не должен быть пустой заглушкой. Он должен объяснять преподавателю, какие рабочие зоны доступны.

Пример структуры:

```text
Контур преподавателя
Подготовка учебных баз, тем, эталонных запросов и SQL-заданий.

[Каталог СУБД] [Учебные базы] [Темы]
[Эталонные запросы] [Задания] [Попытки студентов]
```

Хорошее улучшение:

- сверху краткая цепочка workflow;
- ниже карточки разделов;
- справа или снизу небольшой блок "Рекомендуемый порядок работы".

Не надо:

- больших баннеров;
- иллюстраций;
- рекламного текста;
- сложной аналитики без данных.
