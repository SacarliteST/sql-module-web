# Пункт 4. Единый контракт ProblemDetails

Дата реализации: 2026-07-26.

Статус: `Готово`.

## Контракт

Ошибки API теперь имеют единый JSON-формат:

```json
{
  "title": "Конфликт состояния",
  "status": 409,
  "detail": "Отображаемое описание ошибки.",
  "code": "SqlTask.LinksChangeRequiresDraft",
  "errors": {}
}
```

- `title` — человекочитаемая категория ошибки;
- `status` — HTTP-статус;
- `detail` — человекочитаемое описание конкретной причины;
- `code` — стабильный машинный код для клиентской логики;
- `errors` — ошибки отдельных полей; для ошибок без привязки к полям возвращается пустой объект.

Машинный код больше не передаётся через `title`.

## Отображение доменных ошибок

Результаты application-слоя преобразуются централизованно:

| Тип ошибки | HTTP-статус | `title` |
|---|---:|---|
| Validation | 422 | `Ошибка бизнес-валидации` |
| NotFound | 404 | `Ресурс не найден` |
| Conflict | 409 | `Конфликт состояния` |
| прочие | 500 | `Внутренняя ошибка` |

Исходные `Error.Code` и `Error.Message` сохраняются соответственно в `code` и `detail`.

## Валидация входного запроса

Ошибки FluentValidation возвращаются как `422 Unprocessable Entity`:

```json
{
  "title": "Ошибка валидации запроса",
  "status": 422,
  "detail": "Одно или несколько полей заполнено некорректно.",
  "code": "Request.ValidationFailed",
  "errors": {
    "TaskName": [
      "TaskName обязательно для заполнения."
    ]
  }
}
```

Swagger-метаданные endpoint-ов также изменены с 400 на 422.

## Необработанные исключения

Глобальный обработчик использует тот же контракт и назначает машинные коды:

- `Unhandled.NotFound`;
- `Unhandled.BadRequest`;
- `Unhandled.InternalServerError`.

Текст внутреннего исключения при статусе 500 наружу не раскрывается.

## Swagger и frontend

В Swagger-схемы `ProblemDetails` и `HttpValidationProblemDetails` добавлены поля
`code` и `errors`. Orval-клиент перегенерирован штатной командой, поэтому frontend
получает типизированный машинный код и словарь ошибок без ручного редактирования
generated-файлов.
