# Техдолг IdentityService для админского контура

Дата анализа: 2026-07-20.

Источник анализа: `identity.swagger.json` и сгенерированный Orval-клиент в `src/api/identity`.

## Что уже есть в Identity API

| Метод | Путь | Назначение | Можно использовать в админке |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/login` | Вход пользователя | Да |
| `POST` | `/api/v1/auth/logout` | Выход по refresh token | Да |
| `POST` | `/api/v1/auth/refresh` | Обновление пары токенов | Да |
| `POST` | `/api/v1/auth/register` | Регистрация пользователя со студенческой ролью | Ограниченно |
| `POST` | `/api/v1/users/{id}/roles` | Назначение роли пользователю | Ограниченно |
| `GET` | `/health` | Проверка доступности IdentityService | Да |
| `GET` | `/.well-known/jwks.json` | JWKS для проверки JWT | Не нужно в UI |
| `GET` | `/.well-known/openid-configuration` | OpenID discovery | Не нужно в UI |

Схемы, которые сейчас видит фронт:

- `LoginRequest`
- `RefreshRequest`
- `RegisterRequest`
- `TokenResponse`
- `AssignRoleRequest`
- `ProblemDetails`

## Что фронт может подключить прямо сейчас

- Реальный вход, выход и обновление токена.
- Проверку доступности IdentityService через `/health`.
- Назначение роли пользователю, если фронт уже знает `userId`.

Этого достаточно для базового сценария авторизации, но недостаточно для полноценного админского контура.

## Главные ограничения текущего API

### Нет списка пользователей

В макете админского контура есть окно "Пользователи", но в Identity API нет ручки для получения пользователей.

Нужна ручка:

```http
GET /api/v1/users
```

Минимальные параметры:

- `page`
- `pageSize`
- `search`
- `role`
- `status`

Минимальный ответ:

```ts
type UserListItemDto = {
  id: string;
  email: string;
  displayName: string | null;
  roles: string[];
  status: "Active" | "Blocked";
  createdAt: string;
  lastLoginAt: string | null;
};
```

Ответ лучше сразу сделать постраничным:

```ts
type PagedResponse<T> = {
  items: T[];
  page: number;
  pageSize: number;
  totalCount: number;
};
```

### Нет карточки пользователя

Окно деталей пользователя сейчас может быть только моковым, потому что нет ручки:

```http
GET /api/v1/users/{id}
```

Минимальный ответ:

```ts
type UserDetailsDto = {
  id: string;
  email: string;
  displayName: string | null;
  roles: string[];
  status: "Active" | "Blocked";
  createdAt: string;
  updatedAt: string | null;
  lastLoginAt: string | null;
  blockedAt: string | null;
  blockReason: string | null;
};
```

### Нет админского создания пользователей

`POST /api/v1/auth/register` по текущему описанию регистрирует пользователя со студенческой ролью и возвращает токены. Для админки это неподходящий сценарий: администратор должен создать пользователя, но не должен логиниться за него.

Нужна отдельная ручка:

```http
POST /api/v1/users
```

Минимальный запрос:

```ts
type CreateUserRequest = {
  email: string;
  displayName: string | null;
  password: string;
  roles: UserRole[];
};
```

Минимальный ответ:

```ts
type UserDetailsDto = { /* карточка созданного пользователя */ };
```

На будущее можно добавить режим временного пароля:

```ts
type CreateUserRequest = {
  email: string;
  displayName: string | null;
  roles: UserRole[];
  temporaryPassword?: string;
  requirePasswordChange?: boolean;
};
```

### Управление ролями неполное

Сейчас есть только:

```http
POST /api/v1/users/{id}/roles
```

Проблемы:

- роль в `AssignRoleRequest` сейчас выглядит как свободная строка;
- нельзя снять роль;
- нельзя атомарно заменить набор ролей;
- фронт не может безопасно синхронизировать чекбоксы ролей в карточке пользователя.

Нужен один из вариантов.

Вариант 1, полный replace:

```http
PUT /api/v1/users/{id}/roles
```

```ts
type UpdateUserRolesRequest = {
  roles: UserRole[];
};
```

Вариант 2, отдельное удаление:

```http
DELETE /api/v1/users/{id}/roles/{role}
```

Роли лучше описать enum-ом в OpenAPI:

```ts
type UserRole = "Admin" | "Teacher" | "Student";
```

### Нет блокировки и разблокировки пользователей

В админском контуре нужны действия "Заблокировать" и "Разблокировать".

Нужны ручки:

```http
POST /api/v1/users/{id}/block
POST /api/v1/users/{id}/unblock
```

Минимальный запрос на блокировку:

```ts
type BlockUserRequest = {
  reason: string | null;
};
```

Важно на стороне бэка:

- заблокированный пользователь не должен проходить `login`;
- уже выданные refresh tokens заблокированного пользователя желательно инвалидировать;
- статус блокировки должен возвращаться в списке и карточке пользователя.

### Нет активности пользователя и аудита

Макеты админки подразумевают последние действия и технические события. Сейчас таких данных в Identity API нет.

Минимально нужны ручки:

```http
GET /api/v1/users/{id}/activity
GET /api/v1/audit-events
```

Минимальная модель:

```ts
type AuditEventDto = {
  id: string;
  actorUserId: string | null;
  targetUserId: string | null;
  eventType: string;
  description: string;
  createdAt: string;
};
```

Для первой итерации можно сделать только пользовательскую активность:

```http
GET /api/v1/users/{id}/activity
```

### Нет справочника ролей

Фронт сейчас вынужден знать роли сам. Для маленькой системы это терпимо, но лучше отдать роли с бэка, чтобы админка не расходилась с IdentityService.

Вариант:

```http
GET /api/v1/roles
```

Ответ:

```ts
type RoleDto = {
  code: UserRole;
  title: string;
  description: string | null;
};
```

## Доработки OpenAPI-контракта

### Обязательные поля

В сгенерированных TypeScript-моделях поля выглядят опциональными:

- `LoginRequest.email?: string`
- `LoginRequest.password?: string`
- `AssignRoleRequest.role?: string`
- `TokenResponse.accessToken?: string`
- `TokenResponse.roles?: string[]`

Для фронта это неудобно: он вынужден проверять то, что по бизнес-логике должно быть обязательным.

Нужно явно проставить `required` в OpenAPI-схемах.

Минимально обязательные поля:

- `LoginRequest`: `email`, `password`
- `RefreshRequest`: `refreshToken`
- `RegisterRequest`: `email`, `password`
- `AssignRoleRequest`: `role`
- `TokenResponse`: `accessToken`, `accessExpiresAt`, `refreshToken`, `refreshExpiresAt`, `userId`, `email`, `roles`

### Роли как enum

Сейчас роль выглядит как произвольная строка. Нужно описать enum:

```json
{
  "type": "string",
  "enum": ["Admin", "Teacher", "Student"]
}
```

### Единый формат ошибок

Сейчас в swagger используется `ProblemDetails`. Это хороший вариант, но для UI желательно договориться о формате валидационных ошибок:

```ts
type ValidationProblemDetails = {
  type: string;
  title: string;
  status: number;
  detail: string | null;
  instance: string | null;
  errors: Record<string, string[]>;
};
```

Так фронт сможет нормально подсвечивать поля в формах создания пользователя, назначения ролей и блокировки.

## Этапы доработки IdentityService

Этапы идут в порядке зависимостей. После этапа 2 фронт сможет отказаться от моков в окне
"Пользователи", после этапа 4 будет готов основной рабочий админский контур, после этапа 5 -
мониторинг и аудит.

### Этап 0. Зафиксировать API-контракт и правила администрирования

Цель: убрать неоднозначности до изменения БД и реализации endpoint-ов.

- Ввести `UserRole` со значениями `Admin`, `Teacher`, `Student` и строковой сериализацией в JSON/OpenAPI.
- Перевести существующий `AssignRoleRequest` со свободной строки на `UserRole` либо пометить старый endpoint как переходный.
- Зафиксировать единый `ValidationProblemDetails` с `errors: Record<string, string[]>`.
- Сделать обязательные поля auth-контрактов и `TokenResponse` обязательными в OpenAPI.
- Выбрать атомарный `PUT /api/v1/users/{id}/roles` вместо набора add/remove endpoint-ов: он лучше соответствует чекбоксам ролей на фронте.
- Зафиксировать защитные правила: нельзя заблокировать самого себя, снять у себя `Admin` и удалить последнего активного администратора.
- Зафиксировать поведение токенов при блокировке: refresh-токены отзываются сразу, access-токены живут до истечения короткого TTL.

Результат этапа:

- контракты компилируются;
- Swagger содержит `required`, `UserRole` enum и схему validation errors;
- существующие auth endpoint-ы не меняют успешные сценарии.

### Этап 1. Расширить модель пользователя и подготовить миграцию

Цель: добавить данные, без которых список, карточка и блокировка будут возвращать заглушки.

- Добавить в `ApplicationUser`: `CreatedAt`, `UpdatedAt`, `LastLoginAt`, `BlockedAt`, `BlockReason`.
- Для статуса использовать возможности ASP.NET Core Identity (`LockoutEnabled`, `LockoutEnd`), а `BlockedAt` и `BlockReason` хранить как административные метаданные.
- Создать EF Core migration и обновить model snapshot.
- Заполнять `CreatedAt` при регистрации, административном создании и сидировании.
- Обновлять `LastLoginAt` только после успешного входа.
- Определить индексы для `NormalizedEmail`, дат и фильтра статуса; не добавлять отдельную строковую колонку `Status`, если он однозначно вычисляется из блокировки.

Результат этапа:

- миграция применяется на пустой и существующей БД;
- старые пользователи получают безопасные значения;
- регистрация, login и сидинг покрыты интеграционными тестами новых полей.

### Этап 2. Реализовать read-only контур пользователей

Цель: разблокировать реальный список и карточку пользователя на фронте.

- Добавить `GET /api/v1/users` только для роли `Admin`.
- Поддержать `page`, `pageSize`, `search`, `role`, `status` и стабильную сортировку.
- Ограничить максимальный `pageSize`, например значением 100.
- Добавить `GET /api/v1/users/{id}` только для роли `Admin`.
- Добавить `UserListItemDto`, `UserDetailsDto`, `PagedResponse<T>` в `Contracts`.
- Выполнять запросы без tracking; роли получать без N+1-запросов.
- Возвращать `404` для неизвестного пользователя и `422` для некорректных параметров страницы/фильтров.

Результат этапа:

- фронт может заменить моки в списке и карточке;
- фильтрация, пагинация, пустая страница, `401`, `403`, `404` покрыты интеграционными тестами;
- Swagger пригоден для генерации Orval-клиента без ручной правки типов.

### Этап 3. Добавить административное создание и управление ролями

Цель: реализовать основные изменяющие действия в карточке пользователя.

- Добавить `POST /api/v1/users` только для `Admin`; endpoint не выдаёт токены созданного пользователя.
- Валидировать email, пароль, display name и непустой набор ролей.
- Создавать пользователя и назначать роли как одну бизнес-операцию с компенсацией/транзакцией при ошибке назначения.
- Добавить `PUT /api/v1/users/{id}/roles` с полным набором ролей.
- Проверять защитные правила для текущего и последнего активного администратора.
- Добавить `GET /api/v1/roles`, если роли должны иметь локализованные title/description. Если список ролей статичен, фронт может использовать сгенерированный `UserRole` enum без отдельного endpoint-а.
- Старый `POST /api/v1/users/{id}/roles` оставить временно для совместимости либо удалить только после миграции клиентов.

Результат этапа:

- администратор создаёт Student/Teacher/Admin без смены собственной сессии;
- набор ролей заменяется атомарно и возвращается в карточке;
- duplicate email, неизвестная роль, частичный сбой и защитные правила покрыты интеграционными тестами.

### Этап 4. Реализовать блокировку и отзыв сессий

Цель: завершить рабочий админский контур управления доступом.

- Добавить `POST /api/v1/users/{id}/block` с `BlockUserRequest`.
- Добавить `POST /api/v1/users/{id}/unblock`.
- При блокировке установить Identity lockout, `BlockedAt`, `BlockReason` и отозвать все активные refresh-токены пользователя.
- Запретить login и refresh заблокированному пользователю.
- При разблокировке очистить lockout и административные метаданные блокировки.
- Сделать операции идемпотентными либо явно возвращать документированный `409` при повторе.
- Применить правила защиты от self-block и блокировки последнего активного администратора.

Результат этапа:

- статус немедленно отражается в списке и карточке;
- login/refresh заблокированного пользователя отклоняются;
- после разблокировки новый login снова работает;
- сценарии блокировки и отзыва refresh-токенов покрыты интеграционными тестами.

### Этап 5. Добавить аудит и активность

Цель: дать администратору проверяемую историю важных действий.

- Добавить сущность и таблицу `AuditEvent` с actor, target, типом события, описанием и временем.
- Записывать минимум: успешный login, административное создание пользователя, замену ролей, блокировку и разблокировку.
- Не сохранять пароли, JWT, refresh-токены и другие секреты в описании события.
- Добавить постраничный `GET /api/v1/users/{id}/activity`.
- Добавить постраничный `GET /api/v1/audit-events` с фильтрами по actor, target, event type и диапазону дат.
- Расширенный health/status реализовывать отдельно от аудита и не включать в него чувствительные сведения о конфигурации.

Результат этапа:

- административные действия оставляют аудит в той же бизнес-операции либо через надёжный outbox;
- список событий имеет стабильную сортировку и пагинацию;
- права доступа и отсутствие секретов проверены интеграционными тестами.

### Этап 6. Стабилизация контракта и подключение фронта

Цель: завершить миграцию админских страниц с моков на Identity API.

- Обновить `identity.swagger.json` из собранного IdentityService.
- Выполнить `npm run api:generate`; сгенерированные файлы `src/api/identity` вручную не редактировать.
- Подключать фронт вертикальными срезами: список -> карточка -> создание -> роли -> блокировка -> аудит.
- Для каждой мутации настроить инвалидирование TanStack Query и отображение `ValidationProblemDetails` в форме.
- Удалить моки только после интеграционного smoke-теста соответствующей страницы.
- Обновить этот документ фактическими endpoint-ами и удалить закрытые пункты техдолга.

Результат этапа:

- `npm run api:generate`, `npm run typecheck`, `npm run build` проходят;
- админский контур работает без ручных DTO и моковых данных;
- OpenAPI является единственным источником типов API.

### Обязательная проверка каждого backend-этапа

После каждого этапа:

1. Добавить или обновить интеграционные тесты для новых успешных сценариев, валидации и авторизации.
2. Выполнить `dotnet format IdentityService.sln`.
3. Выполнить `dotnet build IdentityService.sln`.
4. Выполнить `dotnet test IdentityService.sln`.
5. Для этапов, меняющих HTTP-контракт, обновить Swagger и убедиться, что Orval генерирует обязательные поля и enum без ручных исправлений.

## Что делать на фронте до доработки бэка

- Оставить админские страницы на моковых данных.
- Подключить реальный `health` в обзор админки, если нужен быстрый живой индикатор IdentityService.
- Не подключать `assignRole` как основное управление ролями, пока нет списка пользователей и контракта на снятие ролей.
- После доработки swagger сначала выполнить `npm run api:generate`, затем интегрировать страницы по одной: список пользователей, карточка пользователя, создание пользователя, роли, блокировка.
