# План внедрения Identity-клиентов в админский контур

Дата: 2026-07-20.

Цель: постепенно заменить моковые данные админского контура на реальные Identity API-клиенты, сгенерированные Orval.

## Текущее состояние

Identity-клиенты обновлены и содержат нужные контракты:

- `src/api/identity/users/users.ts`
- `src/api/identity/audit/audit.ts`
- `src/api/identity/model/userRole.ts`
- `src/api/identity/model/userListItemDto.ts`
- `src/api/identity/model/userDetailsDto.ts`
- `src/api/identity/model/createUserRequest.ts`
- `src/api/identity/model/updateUserRolesRequest.ts`
- `src/api/identity/model/blockUserRequest.ts`
- `src/api/identity/model/validationProblemDetails.ts`

Сгенерированные файлы в `src/api/identity` вручную не редактировать.

## Общий принцип внедрения

Идём маленькими вертикальными итерациями:

1. сначала подготавливаем тонкую frontend-прослойку над Orval;
2. затем подключаем один экран или одно действие;
3. после каждого смыслового шага выполняем `npm.cmd run typecheck` и `npm.cmd run build`;
4. моки удаляем только после того, как соответствующая часть работает на реальном API.

Dev-сервер агентом не поднимать без необходимости. Если всё же был поднят для проверки, после проверки обязательно остановить.

## Этап 0. Зафиксировать текущую базу

Цель: не смешивать уже сделанные правки с интеграцией API.

Сделать:

- проверить текущие изменения по разделению контуров ролей;
- проверить обновлённый `identity.swagger.json`;
- проверить новый техдолг-документ по IdentityService;
- выполнить `npm.cmd run typecheck`;
- выполнить `npm.cmd run build`;
- сделать отдельный коммит, если проверки проходят.

Результат этапа:

- рабочая область чистая или понятная;
- интеграция Identity-клиентов начинается отдельным набором изменений.

## Этап 1. Тонкая прослойка над Identity users

Цель: не тащить детали Orval прямо в страницы.

Предлагаемая структура:

```text
src/
  entities/
    user/
      model/
        types.ts
      lib/
        user-formatters.ts
      index.ts

  features/
    admin-users/
      api/
        admin-users-api.ts
      lib/
        admin-users-errors.ts
      index.ts
```

Сделать:

- завести frontend-типы или type-alias-ы для пользователя, роли, статуса;
- добавить форматирование ролей, статусов и дат;
- добавить helper для извлечения `data` из успешных Orval-ответов;
- добавить helper для отображения `ProblemDetails` и `ValidationProblemDetails`;
- подготовить функции/хуки для списка, карточки и мутаций.

Рекомендуемые API-операции:

- `listUsers`
- `getUserDetails`
- `createUser`
- `updateUserRoles`
- `blockUser`
- `unblockUser`
- `getUserActivity`
- `listAuditEvents`

Результат этапа:

- страницы не импортируют сгенерированные Orval-клиенты напрямую;
- вся обработка статусов ответа и ошибок собрана в одном месте.

## Этап 2. Реальный список пользователей

Цель: заменить моки на странице "Пользователи" реальным `listUsers`.

Сделать:

- подключить загрузку списка пользователей;
- добавить состояние загрузки;
- добавить состояние ошибки;
- добавить пустое состояние;
- подключить поиск;
- подключить фильтр по роли;
- подключить фильтр по статусу;
- подключить пагинацию;
- сохранить переход в карточку пользователя.

Важно:

- параметры запроса держать в состоянии страницы;
- при изменении поиска/фильтров сбрасывать страницу на первую;
- не удалять моки карточки пользователя на этом этапе, если карточка ещё не подключена к API.

Проверка:

```powershell
npm.cmd run typecheck
npm.cmd run build
```

Результат этапа:

- окно "Пользователи" показывает реальные данные из IdentityService;
- фильтры и пагинация работают через API.

## Этап 3. Read-only карточка пользователя

Цель: заменить мок карточки пользователя на `getUserDetails`.

Сделать:

- подключить загрузку пользователя по `userId` из route params;
- показать основные данные пользователя;
- показать роли;
- показать статус;
- показать даты `createdAt`, `updatedAt`, `lastLoginAt`;
- показать `blockedAt` и `blockReason`, если пользователь заблокирован;
- обработать `404`;
- оставить кнопку возврата к списку.

Важно:

- на этом этапе не подключать изменение ролей и блокировку;
- карточка должна быть стабильной read-only страницей.

Проверка:

```powershell
npm.cmd run typecheck
npm.cmd run build
```

Результат этапа:

- список и карточка пользователя полностью работают на реальном API.

## Этап 4. Создание пользователя

Цель: дать администратору возможность создавать пользователя через `createUser`.

Сделать:

- добавить модальное окно создания пользователя;
- поля формы: `email`, `displayName`, `password`, `roles`;
- роли показывать чекбоксами: `Admin`, `Teacher`, `Student`;
- добавить клиентскую валидацию формы;
- отправлять `CreateUserRequest`;
- после успеха закрывать модалку;
- инвалидировать список пользователей;
- при необходимости переходить в карточку созданного пользователя.

Обработка ошибок:

- `409` - пользователь с таким email уже существует;
- `422` - ошибки валидации полей;
- `401`/`403` - нет доступа или сессия протухла.

Проверка:

```powershell
npm.cmd run typecheck
npm.cmd run build
```

Результат этапа:

- администратор может создать Student/Teacher/Admin без смены собственной сессии.

## Этап 5. Управление ролями

Цель: подключить атомарную замену ролей через `updateUserRoles`.

Сделать:

- добавить редактирование ролей в карточке пользователя;
- использовать полный набор выбранных ролей;
- отправлять `UpdateUserRolesRequest`;
- после успеха обновлять карточку и список;
- показывать ошибки защитных правил бэка.

UX-вариант:

- кнопка "Изменить роли";
- модальное окно с чекбоксами ролей;
- кнопки "Сохранить" и "Отмена".

Обработка ошибок:

- нельзя снять `Admin` у самого себя;
- нельзя оставить систему без активного администратора;
- неизвестный пользователь;
- неизвестная роль;
- валидационные ошибки.

Проверка:

```powershell
npm.cmd run typecheck
npm.cmd run build
```

Результат этапа:

- роли пользователя редактируются через реальный IdentityService.

## Этап 6. Блокировка и разблокировка

Цель: подключить управление доступом пользователя через `blockUser` и `unblockUser`.

Сделать:

- добавить действие "Заблокировать";
- добавить действие "Разблокировать";
- использовать `ConfirmModal`;
- при блокировке дать поле причины;
- после успеха обновлять карточку и список;
- корректно показывать статус пользователя после действия.

Обработка ошибок:

- нельзя заблокировать самого себя;
- нельзя заблокировать последнего активного администратора;
- пользователь не найден;
- пользователь уже заблокирован или уже активен, если бэк возвращает `409`.

Проверка:

```powershell
npm.cmd run typecheck
npm.cmd run build
```

Результат этапа:

- администратор может блокировать и разблокировать пользователей из UI.
