# Общее техническое задание: Фаза 2b

Инструкция для параллельных исполнителей находится в
[`PHASE_2B_AGENT_HANDOFF.md`](./PHASE_2B_AGENT_HANDOFF.md), frontend-доска — в
[`PHASE_2B_FRONTEND_KANBAN.md`](./PHASE_2B_FRONTEND_KANBAN.md).

## 1. Назначение

Фаза 2b переводит SQLModule с бинарной проверки «результат совпал / не совпал»
на составную оценку SQL-решения по шкале от 0 до 100.

Результат фазы — единый механизм, который:

- проверяет результат запроса на основной учебной базе;
- анализирует способ решения через многодиалектный AST;
- начисляет баллы по настроенным преподавателем критериям;
- управляет лимитом попыток и лучшим результатом;
- показывает студенту только разрешённые подсказки;
- сохраняет версию правил, по которой оценивалась каждая попытка;
- одинаково работает в standalone-режиме и при запуске с платформы;
- корректно финализирует прохождение и передаёт итог в Education.

Фаза 2b начинается после отдельной стабилизации фазы 2a.

## 2. Что входит в фазу

1. Настройка преподавателем критериев и их весов.
2. Проходной балл для каждого задания.
3. Nullable-лимит попыток `maxAttempts`.
4. Проверка результата запроса на основной базе.
5. Структурный анализ PostgreSQL и MySQL запросов через AST.
6. Обязательные и запрещённые конструкции.
7. Обязательные и запрещённые таблицы.
8. Управляемые преподавателем группы подсказок.
9. Immutable-версии validation-конфигурации.
10. Оценка и детализация каждой попытки.
11. Лучший результат текущего прохождения.
12. История попыток студента и диагностический журнал преподавателя.
13. Ручная и автоматическая финализация.
14. Standalone progress и возможность начать новое прохождение.
15. Интеграция итоговой оценки с Education.

## 3. Что не входит

- скрытая или теневая база данных;
- генерация скрытых наборов данных;
- штраф за количество использованных попыток;
- оценка производительности или красоты SQL;
- автоматический поиск единственного «правильного» текста решения;
- распределённый sandbox lease между несколькими Docker-host;
- изменение временного контракта `TimeLimitMinutes → ExpiresAt`;
- масштабирование инфраструктуры на несколько хостов.

Обе базы выполнения остаются read-only для SQL студента. В текущей фазе
фактически используется только основной учебный набор.

## 4. Роли и сценарии

### 4.1. Преподаватель

Преподаватель:

1. создаёт задание, схему, данные и эталонный SQL;
2. задаёт `passingScore` и `maxAttempts`;
3. добавляет критерии и назначает им веса;
4. выбирает разрешённые для DBMS конструкции и таблицы;
5. определяет, какие группы правил можно показать студенту;
6. запускает preview проверки эталона;
7. публикует новую validation version только после успешного preview;
8. просматривает попытки, SQL студента и полную диагностику критериев.

### 4.2. Студент

Студент:

1. открывает задание и видит только разрешённые подсказки;
2. отправляет SQL в рамках текущего progress или module session;
3. получает балл попытки, лучший балл и безопасную детализацию;
4. продолжает отправки до финализации или исчерпания `maxAttempts`;
5. может вручную завершить platform-прохождение;
6. в standalone после завершения может начать новое прохождение, не удаляя
   прежнюю историю.

## 5. Модель оценки

Обязательные правила:

- шкала результата — целые числа от 0 до 100;
- `MainDatasetResult` существует ровно в одном экземпляре;
- вес каждого активного критерия — положительное целое число;
- сумма весов равна 100;
- `passingScore` находится в диапазоне от 0 до 100;
- `maxAttempts` равен `null` либо положительному числу в серверном диапазоне;
- простое задание допускает только `MainDatasetResult` с весом 100;
- новая попытка не может уменьшить `bestScore`;
- штраф за предыдущие попытки не применяется.

```text
attemptScore = сумма весов выполненных критериев
bestScore = max(attemptScore всех учитываемых попыток прохождения)
isPassed = bestScore >= passingScore
```

## 6. Критерии

Минимальный набор видов:

```text
MainDatasetResult
RequiredConstruct
ForbiddenConstruct
RequiredTable
ForbiddenTable
```

Первый набор AST-конструкций:

```text
Join
InnerJoin
LeftJoin
RightJoin
FullJoin
GroupBy
Having
Distinct
Subquery
Cte
WindowFunction
```

Точный набор определяется DBMS capabilities. Frontend не хранит собственную
расширенную копию enum. Один объект нельзя одновременно сделать обязательным и
запрещённым. Дубли критериев запрещены.

Структурный критерий подтверждает наличие или отсутствие конструкции, но не
доказывает, что она повлияла на результат. Поэтому критерий результата остаётся
обязательным.

## 7. AST-анализ

Перед реализацией выполняется parser spike для PostgreSQL и MySQL на корпусе
реальных запросов. Выбранная библиотека должна иметь AST и visitor API.

Домен зависит от внутреннего интерфейса анализатора, а не от типов библиотеки.
Адаптер обязан корректно различать:

- комментарии и строковые литералы;
- алиасы и qualified names;
- вложенные запросы;
- CTE;
- quoted identifiers;
- виды JOIN;
- оконные функции.

AST используется для оценки, а не для обеспечения безопасности. Запрет DDL/DML,
read-only права, timeout и изоляция продолжают обеспечиваться sandbox-слоем.

Синтаксическая ошибка в SQL студента расходует попытку. Внутренний сбой или
timeout анализатора считается infrastructure failure, не создаёт учитываемую
попытку и не уменьшает лимит.

## 8. Подсказки и раскрытие данных

Группы подсказок:

```text
Result
RequiredConstructs
ForbiddenConstructs
RequiredTables
ForbiddenTables
```

Преподаватель включает видимость по группам. Видимость не влияет на выполнение
критерия и начисление баллов.

Student API не возвращает:

- эталонный SQL;
- ожидаемые строки;
- невидимые критерии и правила;
- внутренний AST;
- setup/DDL и connection data;
- raw parser, database или sandbox errors.

Teacher API возвращает полную прикладную диагностику, но также не раскрывает
инфраструктурные секреты.

## 9. Версионирование

Опубликованная validation-конфигурация неизменяема. Любое изменение критериев,
весов, passing score, maxAttempts или видимости подсказок создаёт новую версию.

Каждая попытка хранит `ValidationVersionId`. Старые попытки всегда отображаются
и интерпретируются по своей версии, даже если преподаватель изменил задание.

Перед публикацией backend:

1. валидирует конфигурацию и сумму весов;
2. проверяет поддержку критериев выбранным DBMS;
3. разбирает эталонный SQL;
4. выполняет эталон на основной базе;
5. убеждается, что эталон получает 100 баллов;
6. атомарно публикует новую версию.

## 10. Попытки и конкурентность

- `Idempotency-Key` обязателен для submit и сохраняет существующую семантику.
- Повтор идентичного запроса возвращает ту же попытку.
- Другой payload с прежним ключом возвращает конфликт.
- Параллельные запросы не могут превысить `maxAttempts`.
- Номер попытки и резервирование лимита определяет backend.
- Frontend не уменьшает число оставшихся попыток оптимистично.
- SQL-ошибка студента сохраняется как учитываемая попытка.
- Infrastructure failure не учитывается и допускает безопасный повтор.

`maxAttempts` принадлежит SQLModule. `TriesCount` Education используется только
для решения, можно ли создать/возобновить прохождение, и не является вторым
лимитом отправок SQL.

## 11. Progress и режимы работы

### Standalone

Для задания создаётся отдельный `StudentTaskProgress`. После завершения или
исчерпания попыток студент может начать заново. Старый progress и его история
сохраняются, новый связывается с актуальной validation version. Education,
integration outbox и platform return не требуются.

### Platform

Progress связан с `ModuleSession`, созданной через platform launch. Существующий
`ExpiresAt` остаётся источником временного ограничения. Итог передаётся в
Education только после финализации.

## 12. Финализация

Финализация выполняется:

- автоматически при достижении 100 баллов;
- после последней разрешённой попытки;
- при expiry;
- при закрытии сессии Education;
- вручную студентом.

Если студент завершает прохождение ниже `passingScore`, frontend запрашивает
подтверждение, но итоговое состояние повторно определяет backend.

Ручная финализация, expiry-worker, последняя попытка и повторный callback не
могут создать несколько итогов. Атомарно сохраняются `FinalScore = BestScore`,
причина, время и единственная outbox-запись.

При expiry финализация происходит в первом cleanup-проходе до отвязки попыток:

- если попытки были — `FinalScore = BestScore`;
- если попыток не было — `FinalScore = 0`, `isPassed = false`.

Сбой доставки в Education повторяет ту же outbox-запись и не пересчитывает
оценку.

## 13. Журнал попыток

Каждая учитываемая попытка создаёт Kafka-событие для журнала SQLModule.
Преподавателю нужен пагинированный read API с фильтрами по заданию, студенту,
progress/session, версии и результату.

Student history содержит только собственные попытки и безопасный breakdown.
Teacher history содержит submitted SQL, score, версию и полную прикладную
диагностику.

## 14. Архитектурные компоненты

Предварительная модель:

```text
TaskValidationConfiguration
ValidationCheck
TaskValidationVersion
StudentTaskProgress
AttemptCheckResult
AttemptReservation (или эквивалент)
ModuleSessionFinalization
```

`Attempt` расширяется ссылками на validation version и progress, номером,
баллом и признаком учёта в лимите. Конкретная схема хранения выбирается backend,
если публичные гарантии сохраняются.

## 15. API-направления

Минимально требуются:

```text
GET  DBMS validation capabilities
GET  teacher validation configuration
PUT  teacher validation configuration
POST validation preview
GET  student task with safe hints and progress
POST standalone progress start/restart
POST attempt with composite result
GET  student attempt history
GET  teacher attempt journal/details
POST current platform session finalize
```

Точные DTO и ошибки зафиксированы в отдельном frontend/backend контракте. Все
операции описываются в Swagger; generated-клиенты вручную не редактируются.

## 17. Критерии приёмки

1. Эталон нельзя опубликовать, если он не набирает 100.
2. Сумма весов всегда равна 100, `MainDatasetResult` обязателен.
3. Неподдерживаемый DBMS-критерий нельзя сохранить.
4. PostgreSQL и MySQL проходят согласованный parser corpus.
5. Каждая попытка содержит score и immutable validation version.
6. Лучший балл не уменьшается.
7. Параллельные submit не превышают лимит и не создают дубли.
8. Infrastructure failure не расходует попытку.
9. Student не получает скрытые правила и технические данные.
10. Teacher получает полную безопасную диагностику.
11. Standalone работает без Education и Kafka.
12. Platform получает ровно одну итоговую оценку от 0 до 100.
13. Expiry финализируется до отвязки попыток.
14. Старые попытки продолжают читаться по своей validation version.
15. Swagger, Orval, typecheck и production build проходят.
16. Пройдены teacher и student smoke в standalone и platform-flow.

3. Максимальное серверное значение `maxAttempts`.
4. Физическое хранение snapshot validation version.
5. Формат и срок хранения Kafka-событий журнала попыток.
