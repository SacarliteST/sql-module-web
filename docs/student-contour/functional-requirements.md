# Контур студента. Функциональные требования

Документ фиксирует требования к первой реализации студенческого контура SQL Module Web. Он нужен как основа для следующих промтов и маленьких итераций разработки.

## 1. Цель контура

Студент должен войти в SQL-модуль, увидеть доступные темы, учебные базы и SQL-задания в виде дерева `Темы → Базы → Задания`, открыть конкретное задание, написать `SELECT`-решение, отправить попытку на проверку, получить результат выполнения и посмотреть историю своих попыток.

Контур студента не создаёт учебный контент. Темы, схемы, эталонные запросы и задания готовит преподаватель или они заранее заведены через API/Swagger на время разработки.

## 2. Роль и доступ

- Доступ к контуру имеет пользователь с ролью `Student`.
- Пользователь с ролью `Admin` может видеть контур студента для проверки маршрутизации и демонстрации.
- Пользователь без подходящей роли видит экран отсутствия доступа.
- `UserId` для отправки попытки берётся backend-ом из текущей сессии/JWT, фронт не должен передавать его вручную.
- Для тестового запуска фронт показывает все базы, все темы и все задания, которые возвращает API.
- При этом код и UI не должны закреплять правило "студент видит всё" как постоянное бизнес-правило. Нужно оставить задел на будущую фильтрацию по доступам, курсам, группам, назначенным темам или опубликованности заданий.

## 3. Основные пользовательские сценарии

### 3.1. Просмотр доступных заданий

Студент открывает раздел `Студент` и видит рабочий экран с иерархией учебных материалов:

```text
Темы
  Базы
    Задания
```

Минимальный сценарий v1:

- загрузить список заданий;
- загрузить список тем;
- загрузить список учебных баз;
- загрузить список эталонных SQL-запросов для связи заданий с базами;
- в тестовом режиме показывать все задания из API без дополнительной фильтрации на фронте;
- построить дерево `Темы → Базы → Задания`;
- показать название задания;
- показать сложность;
- показать краткий текст условия или начало условия;
- дать возможность открыть задание;
- показать пустое состояние, если заданий нет;
- показать состояние загрузки и ошибку загрузки.

Желательный сценарий после первой итерации:

- поддержать вложенные темы через `parentTopicId`;
- дать фильтр/поиск по названию;
- показать последнюю попытку студента по заданию, если она доступна через API.
- добавить слой будущей фильтрации видимости, чтобы позже заменить тестовый режим "все задания" на "только доступные студенту".

### 3.1.1. Просмотр баз и тем в тестовом режиме

На время тестового запуска студентский контур может показывать вспомогательную информацию, которая позже будет ограничена:

- все темы, которые возвращает API;
- все задания, которые возвращает API;
- все учебные базы/датасеты, если они нужны для выбора или понимания задания.

Это нужно для быстрой проверки сквозного сценария без полной системы назначений. В дальнейшем видимость должна определяться backend-ом или отдельным слоем доступа, а фронт должен уметь принять уже отфильтрованный список.

Связь задания с учебной базой строится через эталонный SQL-запрос:

```text
SqlTask.sqlQueryId → SqlQuery.targetDbId → TargetDb.id
```

Если связь неполная, задание нужно показывать в fallback-группе `Без базы / связь не найдена`, а не скрывать.

### 3.2. Просмотр задания

Студент открывает задание и видит:

- название задания;
- уровень сложности;
- полный текст условия;
- SQL-редактор для решения;
- кнопку `Проверить`;
- область результата проверки;
- историю попыток по этому заданию.

Целевой редактор SQL для проекта — Monaco Editor (`@monaco-editor/react` + `monaco-editor`).

Минимальный редактор первой рабочей итерации может быть обычным `Textarea`, если Monaco ещё не подключён. Подключение Monaco вынести в отдельный шаг, чтобы не смешивать установку зависимости и бизнес-логику.

### 3.3. Отправка решения

Студент вводит SQL-запрос и нажимает `Проверить`.

Фронт отправляет:

```ts
SubmitAttemptRequest {
  taskId: string;
  submittedSql: string;
}
```

Требования:

- запрещать отправку пустого SQL;
- отправлять только `SELECT`-решение на уровне UI-подсказки/валидации, но окончательное правило остаётся на backend;
- блокировать кнопку на время отправки;
- не терять введённый SQL при ошибке;
- после успешной отправки обновлять историю попыток по заданию.

### 3.4. Просмотр результата проверки

После отправки студент видит результат:

- статус выполнения;
- верно/неверно;
- причину результата;
- количество строк результата, если backend вернул `rowCount`;
- длительность выполнения, если backend вернул `durationMs`;
- таблицу фактического результата `actualColumns` + `actualRows`;
- безопасное сообщение об ошибке, если backend вернул `errorMessage`.

Результат должен быть понятным без технических стек-трейсов.

### 3.5. История попыток

Студент должен видеть историю своих попыток:

- на экране задания, отфильтрованную по `taskId`;
- позднее, отдельным экраном `Мои попытки`.

В истории показывать:

- дату начала/создания;
- отправленный SQL;
- статус;
- верно/неверно;
- причину результата;
- длительность;
- количество строк;
- краткое сообщение об ошибке, если есть.

## 4. Экраны v1

### 4.1. `StudentHomePage`

Назначение: стартовая страница студента.

Содержимое:

- заголовок `Рабочая область студента`;
- breadcrumbs;
- список заданий;
- пустое состояние;
- загрузка/ошибка.

В первой реализации можно использовать уже существующий маршрут `/student`.

### 4.2. `StudentTaskPage`

Назначение: решение конкретного задания.

Рекомендуемый маршрут:

```text
/student/tasks/:taskId
```

Содержимое:

- breadcrumbs: `Главная / Студент / Задание`;
- карточка условия;
- редактор SQL;
- кнопка проверки;
- блок результата последней отправки;
- таблица истории попыток по заданию.

### 4.3. `StudentAttemptsPage` (после базового решения)

Назначение: общий список попыток студента.

Рекомендуемый маршрут:

```text
/student/attempts
```

Содержимое:

- таблица попыток;
- фильтр по заданию, если будет удобно;
- пагинация;
- переход к заданию.

## 5. API-зависимости

Использовать только сгенерированные Orval-хуки и типы. Не редактировать файлы в `src/api/sqlmodule` вручную.

Для тестового запуска допустимо использовать общие list-эндпоинты без фильтрации по студенту. В коде такие места нужно держать локализованными, чтобы позже заменить их на фильтрованные эндпоинты или параметры доступа.

### 5.1. Задания

Файл:

```text
src/api/sqlmodule/training/training.ts
```

Ожидаемые операции:

- `useGetAllSqlTasks` — список заданий с пагинацией.
- `useGetSqlTaskById` — получение задания по `id`.
- `useGetAllSqlQueries` — список эталонных SQL-запросов для связи задания с учебной базой.

Связанные типы:

- `SqlTaskResponse`
- `SqlTaskResponsePageResponse`
- `SqlQueryResponse`
- `SqlQueryResponsePageResponse`
- `GetAllSqlTasksParams`

Важные поля `SqlTaskResponse`:

- `id`
- `topicId`
- `taskName`
- `taskText`
- `difficultyLevel`
- `createdAt`
- `updatedAt`

Важные поля `SqlQueryResponse`:

- `id`
- `targetDbId`

### 5.2. Темы

Ожидаемые операции:

- `useGetAllTopics` — список тем.
- `useGetTopicById` — получение темы по `id`.

Связанные типы:

- `TopicResponse`
- `TopicResponsePageResponse`

В первой итерации темы можно не выводить деревом, если API списка заданий не даёт удобной связки. Но требования к будущей группировке нужно учитывать в структуре UI.

### 5.3. Отправка попытки

Операция:

- `useSubmitAttempt`

Запрос:

```ts
SubmitAttemptRequest {
  taskId?: string;
  submittedSql?: string;
}
```

Ответ:

```ts
SubmitAttemptResponse {
  attemptId?: string;
  status?: ExecutionStatus;
  isCorrect?: boolean;
  reason?: CheckReason;
  rowCount?: number | null;
  durationMs?: number | null;
  errorMessage?: string | null;
  actualColumns?: string[];
  actualRows?: string[][];
}
```

HTTP-статусы:

- `201` — попытка проверена и сохранена;
- `400` — ошибка валидации запроса;
- `404` — задание не найдено;
- `409` — эталонный результат задания ещё не готов.

### 5.4. История попыток

Ожидаемые операции:

- `useGetAllAttempts` — список попыток с фильтрами;
- `useGetAttemptById` — попытка по `id`.

Параметры:

```ts
GetAllAttemptsParams {
  Offset?: number;
  Limit?: number;
  TaskId?: string;
  UserId?: string;
}
```

Для студента в UI желательно фильтровать по `TaskId`. `UserId` не передавать вручную, если backend умеет ограничивать выдачу текущим пользователем. Если backend возвращает общие попытки, это нужно отдельно согласовать.

### 5.5. Учебные базы/датасеты

Файл:

```text
src/api/sqlmodule/schema/schema.ts
```

Для тестового запуска можно показывать все базы/датасеты, которые возвращает API.

Ожидаемые операции:

- `useGetAllTargetDbs` — список учебных баз/датасетов;
- `useGetTargetDbById` — получение базы по `id`.

Связанные типы:

- `TargetDbResponse`
- `TargetDbResponsePageResponse`
- `GetAllTargetDbsParams`

Важные поля `TargetDbResponse`:

- `id`
- `dbmsId`
- `dbName`
- `description`
- `isReadOnly`

В будущем список баз должен быть ограничен тем, что доступно студенту через назначенные задания, курс или отдельную модель доступа.

## 6. Отображение статусов и причин

Сгенерированные enum-типы сейчас представлены числами:

- `ExecutionStatus.NUMBER_0`
- `ExecutionStatus.NUMBER_1`
- `ExecutionStatus.NUMBER_2`
- `CheckReason.NUMBER_0` ... `CheckReason.NUMBER_6`

Нужно создать локальные мапперы в коде студенческого контура, не правя generated-файлы.

Предварительная семантика `CheckReason` из ТЗ:

- `Ok`
- `ColumnMismatch`
- `RowCountMismatch`
- `ValueMismatch`
- `SqlError`
- `Timeout`
- дополнительная/неизвестная причина

Если точный числовой порядок не подтверждён backend-ом, в UI использовать осторожные подписи и предусмотреть fallback `Неизвестная причина`.

## 7. Состояния интерфейса

Для каждого API-экрана нужны состояния:

- загрузка;
- ошибка;
- пустой список;
- успешные данные;
- отправка формы;
- ошибка отправки;
- успешный результат.

Ошибки показывать спокойно, без технических подробностей:

- `400` — проверьте введённые данные;
- `401` — сессия истекла, нужен повторный вход;
- `403` — нет доступа;
- `404` — задание не найдено;
- `409` — задание ещё не готово к проверке;
- `5xx`/network — сервис временно недоступен.

## 8. UI-правила

Следовать `docs/testing-system-ui-style.md`.

Для студенческого контура:

- не делать landing page;
- использовать рабочий layout;
- использовать `Page`, `PageHeader`, `PageBreadcrumbs`, `AppCard`, `EmptyState`;
- список заданий делать компактными карточками или таблицей;
- экран задания делать плотным: условие, редактор, результат, история;
- результат SQL показывать таблицей;
- кнопку проверки делать основной синей;
- ошибки проверки показывать через `Alert`;
- пустые состояния показывать текстом без декоративных иллюстраций.

## 9. Нефункциональные требования

- Не редактировать generated Orval API-клиенты.
- Не хардкодить base URL API.
- Monaco Editor выбран как целевой SQL-редактор. Не добавлять его в первый шаг, если задача только собрать контур и требования.
- Не добавлять новые зависимости без отдельного согласования.
- Сохранять работоспособность текущего логина и role guards.
- После реализации запускать `npm run typecheck` и `npm run build`.
- Если агент поднимал dev-сервер для проверки, после проверки его нужно остановить.

## 10. Предлагаемая структура кода

Для реализации студенческого контура использовать Feature-Sliced-lite:

```text
src/
  pages/
    student-home/
    student-task/
    student-attempts/

  features/
    student-materials/
      model/
      ui/

    student-tasks/
      api/
      model/
      ui/

    submit-sql-attempt/
      model/
      ui/

    student-attempts/
      model/
      ui/

  entities/
    sql-task/
      model/
      ui/

    attempt/
      model/
      ui/

    topic/
      model/
      ui/
```

Не обязательно создавать все папки сразу. Создавать по мере появления реального кода.

## 11. Первый порядок реализации

### Итерация 1. Список заданий

- Обновить `StudentHomePage`.
- Подключить `useGetAllSqlTasks`.
- Подключить `useGetAllSqlQueries`.
- Подключить `useGetAllTopics`.
- Подключить `useGetAllTargetDbs` для тестового отображения всех учебных баз.
- Построить дерево `Темы → Базы → Задания`.
- Показать задания внутри соответствующих тем и баз.
- Показать fallback-группы `Без темы` и `Без базы / связь не найдена`.
- Добавить переход на `/student/tasks/:taskId`.
- Обработать loading/error/empty.

### Итерация 2. Экран задания

- Создать `StudentTaskPage`.
- Подключить `useGetSqlTaskById`.
- Показать условие и форму SQL.
- Пока использовать `Textarea`.

### Итерация 3. Отправка решения

- Подключить `useSubmitAttempt`.
- Добавить валидацию непустого SQL.
- Показать результат проверки.
- Показать таблицу `actualColumns` + `actualRows`.

### Итерация 4. История попыток по заданию

- Подключить `useGetAllAttempts` с `TaskId`.
- Показать таблицу попыток под редактором.
- После отправки инвалидировать/обновлять список.

### Итерация 5. Улучшение редактора

- Установить и подключить Monaco Editor (`@monaco-editor/react` + `monaco-editor`).
- Заменить `Textarea` на SQL-редактор.
- Добавить базовую подсветку SQL.

## 12. Открытые вопросы

- Нужно ли backend-у ограничивать `GetAllAttempts` текущим студентом автоматически, если `UserId` не передан?
- Есть ли отдельный признак опубликованности задания, или студент видит все `SqlTask`?
- Какой точный числовой порядок у `ExecutionStatus` и `CheckReason`?
- Нужно ли показывать студенту тему как дерево уже в первой версии?
- Нужно ли хранить черновик SQL-решения локально между переходами?
- Как в будущей версии будет определяться доступность тем, баз и заданий для конкретного студента: курс, группа, назначение преподавателя, публикация задания или отдельный ACL?
