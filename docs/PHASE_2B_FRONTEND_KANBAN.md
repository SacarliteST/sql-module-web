# Kanban frontend: Фаза 2b — составная проверка SQL

## Цель

Перевести teacher и student UI с бинарного результата попытки на оценку от 0
до 100 по версионируемому набору критериев. Преподаватель настраивает веса,
проходной балл, лимит попыток и видимость подсказок. Студент видит только
разрешённую диагностику, лучший балл и состояние текущего прохождения.

Фаза 2b начинается после стабилизации 2a. Скрытые наборы данных и штрафы за
число попыток в неё не входят. Общие требования зафиксированы в
[`PHASE_2B_TECHNICAL_REQUIREMENTS.md`](./PHASE_2B_TECHNICAL_REQUIREMENTS.md).
Для передачи отдельной задачи другому агенту использовать
[`PHASE_2B_AGENT_HANDOFF.md`](./PHASE_2B_AGENT_HANDOFF.md).
Backend ведёт собственную доску; необходимый публичный контракт описан в
[`backend-requirements/2026-09-14-phase-2b-frontend-contracts.md`](./backend-requirements/2026-09-14-phase-2b-frontend-contracts.md).

Статусы: `Backlog`, `Ready`, `In progress`, `Blocked`, `Done`.

## Итерация 1 — контракт и authoring

### F2B-FE-001 — аудит OpenAPI

Сверить Swagger с контрактным документом: teacher validation configuration,
DBMS capabilities, preview, student progress, attempt result, history и
finalization. Отдельно проверить, что student DTO не раскрывают эталон, скрытые
правила, raw AST и данные sandbox.

Выполнено 2026-09-16: backend/frontend Swagger совпадают по SHA-256,
составлена матрица операций и ошибок, проверены enum и student-safe DTO.
Расхождения `API-01`–`API-06` и степень их влияния зафиксированы в
[`PHASE_2B_API_AUDIT.md`](./PHASE_2B_API_AUDIT.md). Живой role-smoke остаётся
частью `F2B-FE-014`.

### F2B-FE-002 — генерация клиента

Перенести backend Swagger и штатно запустить Orval. Generated-файлы вручную не
править. Зафиксировать изменения существующего `Attempt` и удалить временные
ручные адаптеры только после миграции всех потребителей.

Выполнено 2026-09-16: backend/frontend Swagger совпадают по SHA-256
`03FCCA72AB35EEC44290DD922724BC10A46E8AFCD4B83AF76286CF7A78A921F2`.
Штатная команда `npm.cmd run api:generate` успешно сформировала SQLModule и
Identity-клиенты; Identity diff не появился. `npm.cmd run typecheck` и
`npm.cmd run build` прошли. Generated-код вручную не менялся. Новый срез
`Attempt` содержит nullable scoring-поля рядом со старыми `isCorrect`,
`reason` и snapshot: текущие потребители не ломаются, переход на score
выполняется в задачах 008–010. Контрактные замечания остаются в

### F2B-FE-003 — capabilities

Добавить прикладную модель поверх generated DTO. Названия критериев,
конструкций, статусов и групп подсказок локализовать в одном месте. Доступные

Выполнено 2026-09-16: в `src/entities/sql-task/model` добавлены русские метки
критериев, конструкций, статусов, причин завершения и групп подсказок.
`toValidationCapabilitiesModel` строит варианты только из ответа DBMS,
отбрасывает дубликаты, выявляет неизвестные enum и выставляет `canConfigure=false`
при несовместимом ответе. Отображение неизвестного значения безопасно.
Повторный аудит Swagger/Orval не выявил блокеров; typecheck и build прошли.

### F2B-FE-004 — составная оценка

В teacher-форме реализовать список критериев с добавлением, удалением и
изменением веса. `MainDatasetResult` обязателен ровно один раз. Показывать сумму
весов и блокировать сохранение, пока она не равна 100. Здесь же редактируются
`passingScore` и nullable `maxAttempts`; frontend-валидация дублирует, но не
заменяет backend-валидацию.

Выполнено 2026-09-16: на странице задания добавлен редактор текущего черновика
с GET validation и DBMS capabilities, добавлением/удалением критериев,
редактированием весов, проходного балла и лимита. Сохранение блокируется без
единственного `MainDatasetResult`, суммы 100 и допустимых числовых значений.
PUT сохраняет полный draft с version token и существующими группами подсказок;
публикация в этой задаче не выполняется. Значение структурного критерия пока
вводится текстом — в `F2B-FE-005` оно заменяется выбором конструкций и таблиц,
там же добавляется проверка дублей и противоречий. Typecheck и build прошли;
живой UI-smoke перенесён в `F2B-FE-014`.

### F2B-FE-005 — правила и видимость

Для структурных критериев дать выбор поддерживаемой конструкции или таблицы из
актуальной схемы. Не допускать дублей и пар required/forbidden одного значения.
Отдельно настраивать группы подсказок: результат, обязательные/запрещённые
конструкции и таблицы. Добавить preview того, что увидит студент.

Выполнено 2026-09-16: редактор использует стабильные ID таблиц из текущего
schema snapshot и список конструкций из DBMS capabilities. Свободный ввод
заменён выбором, локально блокируются дубли и пары required/forbidden одного
значения, отсутствующие в схеме или capabilities значения. Группы подсказок
настраиваются независимо от критериев; ниже формы показан безопасный preview
видимых студенту правил. Сохранение отправляет выбранные группы. Typecheck и
production build прошли; живой UI-smoke остаётся в `F2B-FE-014`.

### F2B-FE-006 — preview и публикация

Перед сохранением запускать серверный preview эталонного SQL. Отобразить балл
эталона и диагностику каждого критерия. Конфигурацию нельзя опубликовать, если
эталон не набирает 100, parser не поддерживает критерий или схема устарела.
Конфликты версии не перетирать — предложить перезагрузить актуальное состояние.

Выполнено 2026-09-16: форма отправляет текущий draft в серверный preview и
показывает `referenceScore`, analyzer version, результаты критериев и violations.
Изменение draft инвалидирует прежний preview. Сохранение разрешено только после
успешной проверки эталона на 100 баллов; перед публикацией сохранённая версия
проверяется повторно. Публикация — отдельный POST с UUID `Idempotency-Key` и
version token; после неопределённой сетевой ошибки повтор использует тот же
ключ. `409` не перезаписывает форму и предлагает загрузить актуальную версию.
Typecheck и production build прошли; живой UI-smoke остаётся в `F2B-FE-014`.

### F2B-FE-007 — состояние задания

На teacher details показать активную immutable validation version, дату
публикации, проходной балл, лимит и краткую раскладку весов. Изменение создаёт
новую версию; старые попытки продолжают отображаться со своей версией.

Выполнено 2026-09-16: карточка показывает номер и ID активной версии, дату
публикации, проходной балл, лимит и краткую раскладку весов текущей
конфигурации. Отдельно отмечены несохранённые поля и сохранённый, но ещё не
опубликованный черновик. Если `hasUnpublishedChanges=true`, UI прямо говорит,
что видимые веса относятся к черновику, а не обязательно к активной версии:
backend сейчас не предоставляет отдельный read DTO опубликованного snapshot.
Старые попытки привязаны к своей `validationVersionId`; их отображение относится
к `F2B-FE-010`. Typecheck и build прошли, live smoke остаётся в `F2B-FE-014`.

## Итерация 2 — student runtime

### F2B-FE-008 — условие и progress

Показывать разрешённые группы подсказок, `bestScore`, `passingScore`,
`attemptsUsed`, `attemptsRemaining` и состояние прохождения. Не выводить
отсутствующие группы и не пытаться восстановить скрытые правила на клиенте.

Выполнено 2026-09-16: в student task добавлена карточка проверки и progress.
Показаны проходной/лучший балл, использованные/оставшиеся попытки и статус;
подсказки рендерятся только для групп из student DTO. Standalone-студент может
явно начать прохождение с идемпотентным ключом; handoff-режим никогда не вызывает
standalone start. Отправка SQL блокируется, если backend выставил
`canSubmit=false`. После попытки task details обновляются. Убрана старая логика
автоматического возврата в Education по бинарному `isCorrect`: в 2b возврат
должен следовать финализации (`F2B-FE-012`). Typecheck/build прошли;
живой smoke остаётся в `F2B-FE-014`.

### F2B-FE-009 — результат попытки

После отправки показать текущий и лучший балл, факт прохождения и breakdown
доступных студенту критериев. SQL/синтаксическая ошибка является учитываемым
результатом; infrastructure failure не увеличивает локальный счётчик и допускает
безопасный повтор с тем же `Idempotency-Key`.

Выполнено 2026-09-16: новый результат попытки показывает текущий/лучший балл,
проходной порог, номер и остаток попыток, student-safe breakdown и подсказки.
При наличии score итоговый вердикт больше не зависит от старого `isCorrect`;
legacy-ответ без score сохраняет прежнее отображение. SQL/syntax error в `201`
отображается как учтённый результат. `500/503` не создают локального результата
и при неизменённом SQL позволяют повторить отправку с прежним Idempotency-Key.
Typecheck/build прошли; живой UI-smoke остаётся в `F2B-FE-014`.

### F2B-FE-010 — история

Обновить student history под score/version/check summary. Teacher journal
показывает полную диагностику, SQL, номер попытки и validation version с
пагинацией и фильтрами. Один и тот же component не должен случайно раскрывать

Выполнено 2026-09-16: student history показывает балл, номер и версию проверки,
детали — только student-safe scoring из отдельного student endpoint. Teacher
journal получил фильтры по прохождению, версии, баллам и причине завершения;
полная диагностика загружается из teacher detail endpoint при открытии.
Legacy-вердикт сохранён для старых попыток. Typecheck прошёл, live smoke — 014.

### F2B-FE-011 — standalone restart

После финализации или исчерпания лимита показать «Начать заново» с
подтверждением. Новый progress использует актуальную validation version; старый
результат и попытки остаются в истории.

Выполнено 2026-09-16: standalone показывает «Начать заново» после остановки
отправки, запрашивает подтверждение и вызывает restart с UUID-ключом. Неясный
сетевой исход допускает повтор с тем же ключом; handoff-режим restart не
предлагает. После смены progress ID ключ следующей отправки SQL обновляется,
поэтому старая попытка не может быть переиспользована. Typecheck прошёл;
проверка живого UI — 014.

## Итерация 3 — финализация и устойчивость

### F2B-FE-012 — финализация

В platform-режиме дать завершить прохождение вручную. Если лучший балл ниже
проходного и попытки ещё доступны, запросить подтверждение. Обработать состояния
`Finalizing`, `CompletionPending`, `Completed`, expiry и идемпотентный повтор.
В standalone не выполнять platform return и не ждать Education.

Выполнено 2026-09-16: отдельная карточка завершает standalone через student
endpoint, platform-сессию — через current-session endpoint. При досрочном
завершении ниже проходного балла подтверждение обязательно. UI показывает
подтверждённый итог, pending/failed/expired/Finalizing состояния и позволяет
обновить их. Для автоматически завершённой platform-сессии можно получить
итог идемпотентным вызовом finalize. Возврат на платформу доступен только
после `canReturnToEducation=true` и совпадения адреса возврата с исходным
launch-контекстом; перед переходом очищаются handoff-токен и контекст.
Неопределённый сетевой результат повторяется с прежним UUID-ключом.
Typecheck и production build прошли; живой сценарий остаётся в 014.

### F2B-FE-013 — состояния и ошибки

Унифицировать `400/401/403/404/409/422/503`: исчерпан лимит, завершённая или
истёкшая сессия, stale version, неверная конфигурация, parser/sandbox outage.
Нельзя оптимистично уменьшать число попыток до подтверждённого backend-ответа.

Выполнено 2026-09-17: известные backend-коды `Progress.*`,
`ModuleSessionClosed`, `TaskValidation.StaleVersion`,
`IdempotencyRequestInProgress` и `TaskValidation.InfrastructureUnavailable`
преобразуются в понятные действия. После `409/422` в start/restart/finalize
и submit экран повторно читает progress; счётчик попыток не меняется локально.
Повтор ещё выполняющейся отправки сохраняет прежний Idempotency-Key. Для
неопределённого сетевого исхода ключи start/restart/submit/finalize остаются
прежними; успешный ответ сбрасывает их. Teacher-редактор блокируется как stale
только при коде `TaskValidation.StaleVersion`, не при любом `409`.

## Отчёт прогона F2B-FE-014 (2026-09-17)

**Окружение:** Identity (`:5101`), Education (`:5135`), SqlModule.Host (`:5202`,
профили `Integrated`→`Platform` поочерёдно), platform-web (`:5173`), sql-module-web
(`:5174`) — все подняты локально напрямую (без gateway), Postgres/Kafka —
уже работавшие Docker-контейнеры сессии. Аккаунты — `admin@scoodle.local` /
`teacher@scoodle.local` / `student@scoodle.local` из `InitialUsers`.

### Блокер P0 (не специфичен для Phase 2b, но ломает весь standalone-контур) — исправлено в этой сессии

`Backend/SqlModule` в проде (`deploy/compose.yaml`) и в профиле запуска
`Platform` работает с `Auth:Audience=sql-module-api` (для валидации JWT
платформенных сессий). При этом прямой standalone-логин через
`POST /identity/api/v1/auth/login` **всегда** выдаёт токен с аудиторией
`scoodle-api` (`Jwt:Audience` в IdentityService — единственное фиксированное
значение, `LoginHandler` не принимает `audience` от клиента). SqlModule
валидирует JWT только по одному `ValidAudience` (`Web/WebExtensions.cs:47`,
`o.Audience = authOptions.Audience`). В результате **в prod-подобной
конфигурации standalone teacher/student логин в sql-module-web получает 401
на каждый запрос к SqlModule API**, что выглядит как случайный разлогин при
любом переходе между разделами — при том что CONCEPT.md прямо фиксирует:
«Автономный режим является постоянной возможностью, а не временной
заглушкой». Нужно либо научить SqlModule принимать оба audience
одновременно (`ValidAudiences`), либо провести отдельное продуктовое решение
о том, как standalone-логин получает нужный audience. Для прохождения
остального чек-листа профиль SqlModule переключался между `Integrated`
(audience `scoodle-api`, для standalone) и `Platform` (audience
`sql-module-api`, для platform-flow) — совместно они не работают на одном
инстансе.

**Исправлено:** SqlModule зарегистрирован в IdentityService как отдельный
token-exchange клиент (`sql-module-standalone`). Новый `POST
/api/v1/auth/login` на стороне SqlModule (`Web/Features/Auth/StandaloneLogin`)
логинит пользователя в Identity и сразу обменивает токен на
audience `sql-module-api` без `session_id` — тот же паттерн, что
`ModuleAuthoringLink` у Education; секрет клиента остаётся на сервере, в
браузер уходит уже готовый обменянный токен. Frontend (`LoginPage`)
переключён на новый эндпоинт. Проверено живым прогоном: JWT после логина
содержит `aud: sql-module-api`, защищённые эндпоинты SqlModule больше не
отдают `401` на едином `Platform`-профиле (без переключения профилей).

### Блокер (инфраструктурный, не Phase 2b) — исправлено в этой сессии

`POST /api/v1/dbms-dictionaries` с `dbmsSystemName: "mysql"` падал
`409 DbmsDictionary.ProbeFailed` («Received unknown response J for
SSLRequest») даже для валидного `mysql:8.0` — `IDbmsProbe`
(`TestcontainersDbmsProbe`) всегда открывал `NpgsqlConnection` независимо от
выбранной СУБД. Для проверки MySQL-веток (сценарий 1) изначально пришлось
временно поднимать SqlModule.Host с `DbmsCatalog__ProbeEnabled=false`.

Исправлено по ходу этой же приёмки (с явного разрешения пользователя менять
`Backend/SqlModule`): `DbmsProbeSpec` получил поле `DbmsSystemName`, проброшенное
из `Create/Update/ValidateDbmsDictionary`; `TestcontainersDbmsProbe` выбирает
`NpgsqlConnection`/`MySqlConnection` по этому полю (не по порту/имени образа),
кэш-ключ probe тоже учитывает тип СУБД. `MySqlConnector` уже был транзитивной
зависимостью через `ProjectReference` на `Sandbox` — новый NuGet-пакет не
понадобился. Добавлен регрессионный `DbmsProbeTests.ProbeAsync_ValidMySqlConfig_ReturnsSuccess`
(реальный Docker-контейнер `mysql:8.0`). Проверено: `dotnet build
SQLModule.sln` — 0 ошибок/предупреждений; `dotnet test IntegrationTests
--filter DbmsProbeTests` — 5/5 зелёных (~31с), включая новый MySQL-кейс и три
существующих Postgres-кейса без регрессий. `DbmsCatalog__ProbeEnabled=false`
из инструкций выше по тексту актуален только как диагностический режим, не
как обязательный обход. **Изменения не закоммичены** — ждут решения
пользователя, на какую ветку.

### Наблюдение (не баг)

Публикация версии проверки (`Опубликовать проверку`) не делает задание
видимым студенту — для этого отдельно нужно нажать верхнеуровневый
`Опубликовать` (публикация самого `SqlTask`, `PublicationStatus`). Это
осознанно разделённые действия («эталон/оценка» vs «видимость задания»), но
явно нигде не задокументировано — стоит один раз явно прописать в
`CONCEPT.md`/`PHASE_2B_TECHNICAL_REQUIREMENTS.md`, чтобы не путать при
дальнейшей приёмке.

UI-пояснение добавлено 2026-09-17: верхняя кнопка названа «Опубликовать
задание», в редакторе проверки и окне подтверждения прямо указано, что это
разные действия. Историческое наблюдение прогона оставлено выше без изменений.

### Блокер (idempotency-replay) — найден 2026-09-17, исправлено в этой сессии

`POST /api/v1/attempts` документирован так: «Повтор с тем же телом возвращает
исходную попытку без повторного запуска sandbox». Конкурентный прогон
подтвердил это для гонки (второй параллельный запрос с тем же
`Idempotency-Key` корректно получает `409 IdempotencyRequestInProgress`, пока
первый ещё выполняется). Но повтор **после** того как отвечающий запрос сам
завершил прохождение (например, добрал 100 баллов и триггернул
auto-finalization), возвращает не replay исходного `201`, а generic
`409 Progress.NotFound`.

Причина — в `Phase2bSubmitAttemptService.TryHandleAsync`
(`Web/Features/Training/Attempts/SubmitAttempt/Phase2bSubmitAttemptService.cs:53-76`):
для standalone-запроса прогресс ищется через `SingleOrDefaultAsync(... &&
Status == ProgressStatus.Active)` **до** обращения к таблице резерваций
(`IAttemptReservationService`, которая как раз хранит idempotency-квитанции
по `progress.Id`). Как только прогресс переходит в `Completed` (в т.ч. тем же
самым запросом, чей повтор мы пытаемся replay-нуть), этот запрос вообще не
находит прогресс, возвращает `Phase2bSubmitResult(false, null)` и
проваливается в generic-фоллбэк legacy-обработчика
(`SubmitAttemptCommand.cs:115-120`), который ничего не знает про
идемпотентность конкретного Phase 2b запроса и всегда отвечает
`Progress.NotFound`.

Практическое влияние было смягчено тем, что frontend (`F2B-FE-013`) уже умел
перечитывать progress при `409` на submit — студент не застревал, но видел
«задание уже пройдено», а не honest replay.

**Исправлено:** `Phase2bSubmitAttemptService.TryHandleAsync` теперь, если
активный standalone-прогресс не найден, ищет его по существующей резервации
с тем же `Idempotency-Key` (для этого пользователя и задания, без
привязки к статусу) — `FindProgressByIdempotencyKeyAsync`. Подтверждено
через `IntegrationTests/Training/Validation/StudentProgressTests.
Submit_SavesCompositeScoreAndUpdatesProgress`: без фикса тест падал именно
с диагностированной ошибкой (`replay.StatusCode should be Created but was
Conflict — Progress.NotFound`), с фиксом — зелёный. Полный прогон
`IntegrationTests` (без Docker-сьютов) и `UnitTests` (132/132) не показал
регрессий от этого изменения.

конфликт в teacher-редакторе — целенаправленно не воспроизводились (нет

**Вывод: F2B-FE-014 закрыта как `Done`.** Оба найденных блокера — (1) P0
