# AGENTS.md

Инструкции для агентской разработки SQL Module Web.

## Что это за проект

Это фронтенд SQL-модуля для образовательной системы тестирования.

Основная задача модуля: дать преподавателю инструменты для подготовки SQL-заданий, схем данных и проверок, а студенту - интерфейс для решения SQL-заданий и просмотра попыток.

Проект должен постепенно сводиться к единому стилю с родительской системой тестирования, но без прямого копирования чужого фронтенда.

## Технологии

- React 19
- TypeScript
- Vite
- Mantine UI
- React Router
- TanStack Query
- Zustand
- React Hook Form
- Zod
- Orval для генерации API-клиентов
- Monaco Editor для SQL-редактора в студенческом контуре

Не добавлять Bootstrap. Стиль родительской системы повторять через Mantine и локальные CSS-модули/файлы.

## Архитектурный подход

Использовать Feature-Sliced-lite, без фанатичного дробления:

```text
src/
  app/
    config/
    layout/
    providers/
    router/

  pages/
    admin-home/
    teacher-home/
    student-home/

  features/
    auth/
    sql-tasks/
    schema-editor/
    attempts/
    dbms-catalog/

  entities/
    user/
    topic/
    sql-task/
    schema/
    attempt/
    dbms/

  shared/
    http/
    ui/
    lib/
    types/
```

Текущий `src/session` пока оставлен на месте. Переносить его в `features/auth` и `entities/user` нужно отдельной маленькой задачей.

## Существующие важные зоны

- `src/app` - сборка приложения: роутер, layout, providers, runtime config.
- `src/shared/ui` - общие UI-компоненты. Сначала проверять, нет ли там уже подходящего компонента.
- `src/shared/http` - runtime fetch и base URL для API.
- `src/api/identity` - сгенерированный Identity API-клиент.
- `src/api/sqlmodule` - сгенерированный SQL Module API-клиент.
- `src/pages` - страницы верхнего уровня.
- `public/runtime-config.json` - runtime-настройки адресов сервисов.
- `orval.config.ts` - настройка генерации API-клиентов.

## Текущее состояние контуров

- Авторизация работает через IdentityService в standalone-режиме.
- Роли `Admin`, `Teacher`, `Student` ведут в разные контуры.
- Контур администратора уже использует Identity API для пользователей, карточки пользователя и журнала аудита.
- Метрики админского обзора не должны быть статическим мок-значением: если показывается состояние сервиса, метрика должна отражать длительность фактического запроса.
- Контуры преподавателя и студента развиваются поэтапно: сначала проектирование окна и промт, затем маленькая реализация.

## UI-правила

Следовать `docs/testing-system-ui-style.md`.

Коротко:

- интерфейс должен быть спокойным рабочим инструментом, не landing page;
- тёмная верхняя панель;
- светлая нейтральная рабочая область;
- компактные формы;
- хлебные крошки на вложенных страницах;
- карточки с тонкой рамкой, лёгкой тенью и малым радиусом;
- таблицы плотные, с рамками и hover-состоянием;
- primary-действия синие;
- secondary-действия серые или outline;
- destructive-действия красные;
- создание/редактирование/удаление предпочтительно через модальные окна;
- пустые состояния простым текстом, без декоративных hero-блоков.

Для SQL-редактора использовать Monaco Editor. Подключать его отдельной итерацией, чтобы не смешивать настройку редактора с бизнес-логикой отправки попыток.

## Общие UI-компоненты

Перед созданием нового визуального паттерна проверить `src/shared/ui`.

Уже есть:

- `Page`
- `PageHeader`
- `PageBreadcrumbs`
- `AppCard`
- `EmptyState`
- `ConfirmModal`
- `FormActions`

Если компонент нужен повторно, выносить его в `shared/ui`. Если он связан с бизнес-сущностью, размещать ближе к `entities` или `features`.

## API и генерация

API-клиенты генерируются Orval.

Команда:

```bash
npm run api:generate
```

Не редактировать вручную сгенерированные файлы в:

- `src/api/identity`
- `src/api/sqlmodule`

Если нужно изменить поведение запросов, смотреть:

- `src/shared/http/identity-fetch.ts`
- `src/shared/http/sqlmodule-fetch.ts`
- `src/shared/http/create-runtime-fetch.ts`
- `orval.config.ts`

## Runtime config

Адреса сервисов задаются через:

```text
public/runtime-config.json
```

Не хардкодить base URL сервисов прямо в компонентах.

Текущие ключи:

- `identityApiUrl`
- `sqlModuleApiUrl`
- `basePath`

## Auth и роли

Поддерживаемые роли:

- `Admin`
- `Teacher`
- `Student`

После логина пользователь перенаправляется на маршрут по роли.

Не ломать текущий сценарий входа через IdentityService.

## Команды проверки

После правок запускать:

```bash
npm run typecheck
npm run build
```

Если менялась генерация API:

```bash
npm run api:generate
npm run typecheck
npm run build
```

## Dev-сервер

Не поднимать dev-сервер без необходимости.

Если dev-сервер был поднят агентом для проверки, после проверки его обязательно нужно остановить.

Пользователь поднимает фронт для ручного тестирования сам.

Если нужно поднять сервер на Windows и PowerShell блокирует `npm.ps1`, использовать:

```powershell
npm.cmd run dev
```

## Стиль работы

- Делать задачи маленькими итерациями.
- Не переписывать весь проект за один шаг.
- Не трогать unrelated-файлы.
- Не удалять пользовательские изменения.
- Не делать бизнес-функциональность внутри чистого рефакторинга.
- Не добавлять новые зависимости без явной необходимости.
- Перед переносом файлов оценить стоимость изменения импортов.
- После каждого смыслового шага держать проект в собираемом состоянии.

## Что нельзя делать без отдельного согласования

- Подключать Bootstrap.
- Удалять runtime config.
- Удалять Orval config.
- Менять base URL сервисов.
- Редактировать сгенерированные API-клиенты вручную.
- Делать глобальный редизайн за пределами поставленной задачи.
- Запускать долгие сетевые установки зависимостей без необходимости.
