# Техническое задание — sql-module-web

Документ задаёт требования к фронтенду модуля **SQLModule** и **порядок разработки**.
Дополняет `CONCEPT.md` (архитектура и стек) и `ROADMAP.md` (статус по фазам).
Статусы готовности по пунктам ведутся в `ROADMAP.md`.

---

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Наименование | sql-module-web — пользовательский интерфейс модуля SQLModule |
| Тип | Одностраничное приложение (SPA), встраиваемое в хост-систему |
| Текущий режим | Standalone (автономная разработка и демонстрация) |
| Целевой режим | Embedded (виджет/компонент внутри хост-системы) |
| Бэкенд | SQLModule API (основной) + IdentityService (аутентификация, только standalone) |
| Стек | React + TypeScript, Vite, Mantine, TanStack Query, Zustand, RHF+Zod, Monaco, React Flow, orval |

---

## 2. Назначение и цели

Предоставить рабочий интерфейс двух контуров SQL-тренажёра — преподавателя (создание контента) и
студента (решение задач) — поверх готовых эндпоинтов SQLModule, с авторизацией через IdentityService.

Критерии успеха v1:
- Преподаватель через UI проходит цикл: СУБД → схема (с валидацией) → данные → задание с эталоном.
- Студент входит, решает `SELECT` в редакторе и получает корректный вердикт.
- Приложение собрано так, что его можно встроить в хост без переписывания фич (см. §3, §5).

---

## 3. Режимы работы и конфигурация

ТР-3.1. Приложение поднимается единой функцией `mount(element, config)`; standalone-входная точка
(`main.tsx`) лишь вызывает `mount` с конфигом из переменных окружения.

ТР-3.2. `config` включает: URL SQLModule API, URL IdentityService (для standalone), base-path роутера,
источник токена (`TokenProvider`), локаль/тему (опционально).

ТР-3.3. Источник токена абстрагирован интерфейсом `TokenProvider`:
- standalone-реализация: встроенный login + хранение + refresh;
- embedded-реализация (задел): возвращает токен, переданный хостом.
Фичи обращаются только к интерфейсу и не знают, откуда токен.

ТР-3.4. Никаких жёстких предположений о корне (`/`) и о глобальном `window`-состоянии: всё через `config`.

---

## 4. Роли и права

| Роль (из JWT) | Доступ |
|---|---|
| `Teacher` | Контур преподавателя: каталог СУБД, конструктор схемы, данные, задания, эталоны |
| `Student` | Контур студента: задания, решение, свои попытки |
| `Admin` | Спец-экранов в модуле нет (управление пользователями — у хоста/Identity) |

ТР-4.1. Маршруты защищены guard-ами по роли; при отсутствии прав — корректный редирект/заглушка.

---

## 5. Архитектурные требования

ТР-5.1. Стек и структура — по `CONCEPT.md` (§6–7). Сгенерированный orval-слой (`src/api/*`) не правится руками.

ТР-5.2. Embed-readiness — по `CONCEPT.md` §5: единая точка монтирования, конфигурируемый base-path,
pluggable `TokenProvider`, самодостаточная тема, конфиг через параметры.

ТР-5.3. Server-state — только через TanStack Query (кэш, инвалидация после мутаций). Session-state
(токен/роль/конфиг) — в Zustand. Состояние форм — в React Hook Form.

## 6. Порядок разработки

Порядок продиктован зависимостями: без каркаса и сессии нельзя строить экраны; без контента
преподавателя студенту нечего решать. Каждая фаза — отдельный промт для агента и проверяемый результат.

| Этап | Содержание | Результат (Definition of Done) |
|---|---|---|
| **0. Каркас** | Vite+TS, структура `src/`, Mantine (тема/нотификации/модалки), React Router (base-path), TanStack Query, Zustand, `mount()`, env-конфиг, http-клиент с интерсептором | `npm run dev` поднимает приложение с layout-заглушкой; сборка и тип-чек проходят |
| **1. Сессия и вход (standalone)** | `TokenProvider` (standalone), экран Login (RHF+Zod), хранение access(память)+refresh(storage), чтение роли из JWT, refresh-on-401, guard-маршруты | Логин выдаёт токен, защищённые маршруты доступны по роли, по 401 идёт автоматический refresh, отзыв цепочки → разлогин |
| **2. Каталог СУБД** | orval-клиент SQLModule; списки и формы `DbmsDictionary`, `PhysicalType`, `ParameterDefinition` (CRUD, валидация Docker-конфига через `validate`) | Преподаватель создаёт/редактирует СУБД и типы; ошибки бэкенда (409/422) показываются на форме |
| **3. Конструктор схемы и данные** | `TargetDb`; визуальный конструктор на React Flow (таблицы/колонки/связи) → `ValidateSchema` → `CreateSchema` (сборка `CreateSchemaRequest` с `TempId`); редактор данных (`DataRecord`/`CellValue`) | Схема валидируется в контейнере и сохраняется атомарно; ошибки DDL показываются понятно; датасет наполняется данными |
| **4. Задания и эталоны** | Темы (`Topic`, дерево + перемещение), создание `SqlQuery` (с вычислением золотого результата), `SqlTask`; просмотр золотого результата | Преподаватель создаёт эталон (золотой результат считается на бэкенде) и задание, привязанное к теме |
| **5. Решение студента** | Дерево тем/заданий; экран задания (условие + Monaco); `SubmitAttempt`; грид результата + вердикт (`CheckReason`), подсветка расхождений; история попыток | Студент отправляет `SELECT`, видит результат и корректный вердикт; попытки сохраняются и доступны в истории |
| **6. Полировка и embed-проверка** | Единые состояния загрузка/ошибка/пусто, тосты, адаптив, доступность; мониторинг попыток для преподавателя; пробное монтирование в тестовый хост | Сценарий демки проходит end-to-end; модуль монтируется в пустой хост через `mount()` с внешним токеном |

> Рекомендуемый порядок — преподаватель раньше студента (контент — предусловие решения) и риск-первый
> (конструктор схемы — самый сложный UI — берётся в середине, не в конце). При необходимости ускорить
> проверку «ядра» можно временно наполнить контент через API/Swagger и собрать этап 5 раньше этапов 3–4.

## 7. Функциональные требования по экранам

### 7.1. Аутентификация (standalone)
- ФТ-1.1. Экран входа: email + пароль; вызов `POST /auth/login`; ошибки 401 — единым сообщением
  «неверный email или пароль» (бэкенд не различает причину).
- ФТ-1.2. (Опц.) экран регистрации: `POST /auth/register` (по умолчанию роль Student).
- ФТ-1.3. Хранение токенов и refresh-флоу: access в памяти, refresh в storage; `POST /auth/refresh`
  при 401 с повтором запроса; при отозванной цепочке — выход и редирект на вход.
- ФТ-1.4. Роль читается из JWT; UI и маршруты подстраиваются под роль.

### 7.2. Каталог СУБД (Teacher)
- ФТ-2.1. Список `DbmsDictionary` (постранично), создание/редактирование/удаление; пароль СУБД
  не отображается в ответах.
- ФТ-2.2. Проверка Docker-конфигурации без сохранения (`/validate`); индикация результата.
- ФТ-2.3. Управление `PhysicalType` и `ParameterDefinition`, привязанными к СУБД.
- ФТ-2.4. Ошибки 409 (дубль/используется) и 422 (валидация) показываются на форме.

### 7.3. Конструктор схемы и данные (Teacher)
- ФТ-3.1. Создание `TargetDb` (датасет: СУБД + имя схемы).
- ФТ-3.2. Визуальный конструктор (React Flow): добавление таблиц (узлы), колонок (тип из `PhysicalType`,
  флаги PK/NOT NULL, параметры), связей (рёбра-FK с правилами ON DELETE/UPDATE).
- ФТ-3.3. «Проверить» → `ValidateSchema` (прогон DDL в контейнере), показ ошибок DDL без сохранения.
- ФТ-3.4. «Сохранить» → `CreateSchema` (атомарно; сборка `CreateSchemaRequest` с `TempId`).
- ФТ-3.5. Наполнение датасета: строки `DataRecord` и значения ячеек `CellValue` через таблицу-редактор.
- ФТ-3.6. (Учесть бэкенд-долг) после финализации схема может стать неизменяемой — UI блокирует правку.

### 7.4. Задания и эталоны (Teacher)
- ФТ-4.1. Дерево тем `Topic` с созданием/перемещением (`MoveTopic`).
- ФТ-4.2. Создание `SqlQuery`: текст эталона + датасет; при создании бэкенд считает «золотой» результат —
  показать его пользователю; обработать ошибку «эталон невалиден».
- ФТ-4.3. Создание `SqlTask`: тема, эталон (`SqlQueryId`), название, текст, сложность.

### 7.5. Решение студента (Student)
- ФТ-5.1. Список доступных тем/заданий.
- ФТ-5.2. Экран задания: условие + SQL-редактор (Monaco), кнопка «Проверить».
- ФТ-5.3. Отправка `SubmitAttempt`; показ грида результата (`QueryResultSet`) и вердикта
  (`IsCorrect` + `CheckReason`: Ok/ColumnMismatch/RowCountMismatch/ValueMismatch/SqlError/Timeout).
- ФТ-5.4. Подсветка/пояснение расхождения с эталоном по причине вердикта; для SQL-ошибки/таймаута —
  безопасное сообщение.
- ФТ-5.5. История попыток студента по заданию (статус, корректность, время, длительность).

### 7.6. Мониторинг (Teacher, этап 6)
- ФТ-6.1. Просмотр попыток студентов по заданию (агрегаты, фильтры).

## 8. Нефункциональные требования

- НФТ-1. **Производительность:** ленивая загрузка тяжёлых экранов (Monaco, React Flow), пагинация списков,
  кэш TanStack Query.
- НФТ-2. **Безопасность токенов:** access — в памяти; refresh — в storage с пометкой о риске XSS и
  направлением на httpOnly-cookie/BFF в проде; токен не логируется.
- НФТ-3. **Обработка ошибок:** единые состояния загрузка/ошибка/пусто; маппинг 401/403/404/409/422/5xx
  на понятные сообщения; ошибки 422 — на поля форм.
- НФТ-4. **Доступность и адаптив:** клавиатурная навигация, контраст, корректная работа на ноутбучных
  разрешениях.
- НФТ-5. **Готовность к i18n:** тексты вынесены, чтобы при необходимости добавить локализацию.
- НФТ-6. **Совместимость встраивания:** изоляция темы/стилей, отсутствие конфликтов глобального состояния
  с хостом.
- НФТ-7. **Качество кода:** TypeScript strict, ESLint/Prettier, тип-чек и сборка в CI-проверке;
  сгенерированный orval-слой не правится руками.

---

## 9. Зависимости и допущения

- Оба сервиса отдают актуальный **OpenAPI-документ** и имеют включённый **CORS** для адреса фронта.
- Согласованы имена claim (`sub`, `role`, `name`, `email`) и ролей (`Student`/`Teacher`/`Admin`).
- В v1 модуль работает в **standalone**; embedded — задел (точка монтирования, base-path, TokenProvider),
  полноценная интеграция в хост — отдельный этап.
- Управление пользователями/ролями и полноценный OIDC-флоу — вне модуля.

---

## 10. Критерии приёмки v1 (сквозной сценарий)

1. Преподаватель входит, создаёт СУБД (с успешной проверкой Docker-конфига).
2. Создаёт `TargetDb`, в конструкторе собирает схему из ≥2 связанных таблиц, проходит валидацию, сохраняет.
3. Наполняет датасет данными.
4. Создаёт эталонный `SqlQuery` (золотой результат посчитан) и `SqlTask` в выбранной теме.
5. Студент входит, открывает задание, пишет `SELECT`, получает вердикт «верно» на корректном решении и
   осмысленную причину — на неверном.
6. Попытки студента сохраняются и видны в истории.
7. Приложение монтируется в пустой тестовый хост через `mount()` с внешним токеном (embed-готовность).
