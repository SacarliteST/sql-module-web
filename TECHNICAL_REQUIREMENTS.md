# Технические требования к SQL Module Web

Актуализировано: 2026-09-12.

Документ фиксирует действующие требования и направление второй итерации.
Фактические статусы отдельных задач ведутся в канбан-досках каталога `docs`.

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Наименование | `sql-module-web` |
| Тип | React SPA с самостоятельным и платформенным запуском |
| Backend | SQL Module API и IdentityService; Education для platform-flow |
| Роли | `Admin`, `Teacher`, `Student` |
| Стек | React 19, TypeScript, Vite, Mantine, TanStack Query, Zustand, React Hook Form, Zod, Monaco, React Flow, ELK, Orval |
| API-конфигурация | `public/runtime-config.json` |

## 2. Цели

Система должна обеспечивать полный цикл практического обучения SQL:

1. преподаватель создаёт тему, учебную базу, схему, данные, задание и эталон;
2. студент открывает опубликованное задание, пишет SQL и получает результат;
3. попытка сохраняется и доступна в истории;
4. модуль работает автономно и через безопасный переход из Scoodle;
5. platform-flow передаёт итоговую оценку по 100-балльной шкале.

Первая итерация реализует этот цикл. Вторая итерация должна подтвердить его в
production-like среде, снять ограничения масштабирования и развить инструменты
работы со схемой и SQL.

## 3. Режимы запуска и сессия

### 3.1. Standalone

- Вход выполняется через IdentityService.
- Поддерживаются access и refresh token.
- Ответ 401 запускает предусмотренный refresh/logout lifecycle.
- Standalone должен работать без Education, Kafka и платформенной сессии.
- Платформенный запуск не должен удалять сохранённую standalone-сессию.

### 3.2. Student handoff

- Публичный маршрут: `/launch`.
- Access token передаётся только во fragment `#access_token=...`.
- Fragment удаляется через `history.replaceState` до первого сетевого запроса.
- Токен хранится только в `sessionStorage`, refresh token отсутствует.
- Допускается только роль `Student` и audience `sql-module-api`.
- `GET /module-integration/sessions/current` является источником `taskId`,
  `returnUrl`, `sessionId` и `expiresAt`.
- Query string и непроверенные значения URL не являются источником этих данных.
- Правильная попытка активной сессии переводит пользователя на доверенный
  `returnUrl`; standalone-попытка не вызывает редирект.

### 3.3. Teacher handoff

- Публичный маршрут: `/teacher/launch`.
- Принимаются роли `Teacher` и `Admin`.
- Токен хранится только в `sessionStorage`, без refresh.
- `ModuleSession`, `session_id`, student launch context и `sessions/current` не
  используются.
- После проверки пользователь переходит к `/teacher/topics`.
- Истечение токена показывает безопасный экран повторного запуска с платформы.

### 3.4. TokenProvider

- Все HTTP-клиенты получают access token через единый интерфейс.
- Generated Orval-код не читает storage напрямую.
- Активный provider переключается между standalone и handoff.
- Logout, 401 и неуспешный launch очищают только соответствующее временное
  состояние и не смешивают режимы.

## 4. Роли и права

| Роль | Разрешённый контур |
|---|---|
| `Student` | Student-safe каталог, решение и собственная история |
| `Teacher` | Темы, базы, схемы, задания, эталоны и журнал попыток |
| `Admin` | Identity admin и преподавательский авторинг через `ContentAuthor` |

- Маршруты frontend защищаются role guards.
- Backend остаётся обязательным источником авторизации.
- Student не получает teacher DTO, эталон, чужие попытки или неопубликованный
  контент даже при прямом запросе.

## 5. Архитектурные требования

- Приложение монтируется через `mount(element, config)`.
- `basePath` и адреса API поступают из runtime config.
- Server state управляется TanStack Query.
- Session state управляется Zustand и `TokenProvider`.
- Формы используют React Hook Form и Zod там, где это оправдано.
- `src/api/*` генерируется Orval и вручную не редактируется.
- При изменении API выполняется последовательность Swagger → Orval → typecheck →
  production build.
- Общие UI-паттерны переиспользуются через `shared/ui`.
- Тяжёлые маршруты, Monaco и ER-компоненты загружаются лениво.

## 6. Требования к контуру преподавателя

### 6.1. Темы и задания

- Иерархия тем поддерживает создание, изменение, удаление и перемещение.
- Задание содержит название, условие, сложность, тему, учебную базу, статус
  публикации и один эталонный запрос.
- Отношение задания и эталона — один к одному.
- Название эталона пользователю не требуется.
- Эталон создаётся и редактируется в контексте задания; выбор произвольного
  эталона из всей базы отсутствует.
- Backend capability flags определяют допустимые операции; frontend не должен
  восстанавливать правила только по косвенным данным.

### 6.2. Учебные базы и схема

- База создаётся визуально либо из пользовательского DDL.
- Выбор типа колонки ограничен физическими типами выбранной СУБД.
- Порядок таблиц и колонок задаётся drag-and-drop без числового поля порядка.
- Внешние ключи создаются только между существующими совместимыми колонками.
- Validate и Apply отображают одни и те же ограничения.
- Violation должен быть привязан к таблице, колонке или связи по `path`.
- Безопасные изменения не требуют подтверждения.
- Запрещённые изменения показывают `code`, `severity`, описание и точное
  `affectedRows` без попытки повторного применения.
- Существующие идентификаторы и данные не должны теряться при безопасном diff.

### 6.3. Исходные данные

- Пользователь добавляет, изменяет и удаляет строки учебной базы.
- Значения валидируются с учётом типа и nullable-контракта.
- Read-only состояние не блокирует первичную настройку новой базы.
- Ошибки конфликтов и валидации показываются рядом с релевантным действием.

### 6.4. Эталонный SQL

- Редактор реализован на Monaco.
- Сохранение запускает backend-валидацию и вычисление эталонного результата.
- Эталон, превышающий student snapshot limit, не делает задание нерешаемым:
  серверное сравнение выполняется независимо от усечённого snapshot.

### 6.5. Попытки студентов

- Журнал поддерживает серверные фильтры по заданию, результату и студенту.
- Студент выбирается по стабильному ID, отображается человекочитаемой подписью и
  восстанавливается после reload.
- Детали показывают SQL, вердикт, длительность, время, автора и фактический
  snapshot в пределах политики доступа.

## 7. Требования к контуру студента

### 7.1. Каталог и карточка

- Отображаются только опубликованные и доступные задания.
- Поддерживаются тема, поиск, сложность и пагинация.
- Карточка содержит условие, правила выполнения и student-safe схему.
- Эталонный SQL, золотой результат и служебные идентификаторы не раскрываются.

### 7.2. SQL-редактор и черновик

- Решение редактируется в Monaco с клавиатурными действиями и fallback.
- Черновик разделяется по пользователю и заданию, переживает reload и очищается
  явно.
- SQL, выбранный из истории, применяется однократно и не перезаписывает более
  свежий черновик после reload.
- Размер локального черновика ограничивается.

### 7.3. Отправка попытки

- Каждый новый payload получает UUID `Idempotency-Key`.
- Повтор после неопределённой сетевой ошибки использует прежний ключ.
- Изменение SQL или задания создаёт новый ключ.
- Повторное нажатие не создаёт конкурентные отправки.
- Ответы 400/401/403/404/409/422/5xx и timeout отображаются безопасно.

### 7.4. Результат и история

- Вердикт отображает `isCorrect`, причину и длительность.
- `actualRows` поддерживает ячейки `string | null`.
- Усечённый snapshot явно помечается.
- Большие значения не должны ломать таблицу и должны открываться полностью по
  действию пользователя.
- История ограничена текущим студентом и поддерживает пагинацию и фильтры.
- Snapshot попытки доступен после reload и не зависит от последнего submit state.

## 8. Интеграционные требования

- Platform-профиль SQL Module API принимает audience `sql-module-api`.
- Standalone-профиль продолжает принимать свой штатный audience.
- Student submit проверяет `session_id`, владельца, task, статус и срок сессии до
  запуска sandbox.
- Первая правильная попытка создаёт единственное завершение с оценкой 100.
- Kafka используется для событий, HTTP — для передачи оценки в Education.
- Outbox/retry не создаёт дубликаты при сбоях и рестарте.
- Ошибка внешнего сервиса не должна влиять на standalone-попытки.

## 9. Нефункциональные требования

### 9.1. Производительность

- Teacher, Student и Admin routes разделяются на ленивые chunks.
- Monaco и React Flow не входят в initial chunk.
- Для initial, Monaco и ER chunks фиксируются проверяемые бюджеты.
- Списки используют серверный поиск и пагинацию; лимит 100 не считается полной
  загрузкой справочника.
- `chunkSizeWarningLimit` не повышается вместо оптимизации.

### 9.2. Безопасность

- Токены и секреты запрещено выводить в URL query, логи, telemetry, уведомления и
  ProblemDetails.
- Handoff fragment очищается немедленно.
- `sessionStorage` handoff не содержит refresh token.
- CSP, `Referrer-Policy` и SPA fallback проверяются на reverse proxy.
- Raw sandbox errors не показываются пользователю.
- Field errors отображаются только по разрешённым `code/path`.
- Разрушительные изменения схемы не подтверждаются на клиенте, а запрещаются
  backend.

### 9.3. Качество и эксплуатация

- TypeScript typecheck и production build обязательны после каждой задачи.
- Ошибки имеют единый пользовательский стиль и, после стабилизации контракта,
  единый trace/correlation ID.
- Интерфейс доступен с клавиатуры и пригоден для ноутбучных разрешений.
- Generated-контракты не содержат числовые `NUMBER_*` enum.
- После стабилизации добавляются минимальные unit/component tests критической
  логики и автоматизированный smoke на тестовом окружении.

## 10. Объём второй итерации

### 10.1. Обязательный объём

1. Production smoke student и teacher handoff.
2. Проверка TLS, proxy routes, SPA fallback, CSP и `Referrer-Policy`.
3. Серверное масштабирование teacher-списков и student history filter.
4. Route-level code splitting и bundle budgets.
5. Интерактивная ER-диаграмма с синхронизацией формы и violations.
6. Monaco completion по схеме и SQL-диалекту.
7. Улучшения result grid, дат, ошибок, форматирования и черновиков.
8. Минимальная регрессионная защита после стабилизации UX и контрактов.

### 10.2. Зависимости backend

- endpoints поиска/пагинации возвращают стабильные `id` и display label;
- выбранная сущность может быть загружена по ID вне текущей страницы;
- ProblemDetails имеет стабильные `code`, `path` и единый trace ID;
- student-safe schema содержит только сведения, необходимые для completion;
- типы и функции SQL-диалекта доступны из каталога либо зафиксированного
  frontend-адаптера без раскрытия инфраструктуры.

### 10.3. Не входит без отдельного решения

- назначения заданий группам и отдельным студентам;
- дедлайны, лимиты попыток и проходной балл;
- аналитические агрегаты преподавателя;
- импорт и экспорт пакетов учебного контента;
- асинхронная попытка и server-side cancel;
- шифрование `sessionKey` at rest;
- полноценный OAuth2/OIDC redirect flow.

## 11. Критерии приёмки второй итерации

1. Standalone Teacher/Student сценарий проходит на тестовом сервере.
2. Student platform-flow проходит от запуска до возврата с оценкой 100.
3. Teacher platform-flow позволяет создать полный набор учебного контента.
4. Токены не обнаруживаются в адресах, логах и referrer; production-заголовки
   безопасности присутствуют.
5. Выбор сущностей работает при объёме более 100 записей и восстанавливается по URL.
6. Начальный bundle не загружает Monaco, React Flow и страницы чужих контуров.
7. ER-диаграмма синхронизирована с формой и подсвечивает backend violations.
8. Monaco предлагает только student-safe объекты выбранной учебной схемы.
9. Большие и nullable результаты не ломают интерфейс.
10. Typecheck, production build, bundle budgets и согласованный набор тестов проходят.
