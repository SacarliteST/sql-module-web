# sql-module-web — концепция и документация

> Фронтенд практического модуля **SQLModule**. Разрабатывается как **самостоятельное приложение (SPA)**,
> с расчётом на последующее **встраивание в хост-систему**. Документ описывает назначение, роли, стек,
> архитектуру, режимы работы и интеграцию. Детальные требования — в `TECHNICAL_REQUIREMENTS.md`, этапы — в `ROADMAP.md`.

---

## 1. Контекст

**SQLModule** — практический модуль платформы Scoodle: интерактивная «песочница» для отработки SQL.
Серверная часть готова: эндпоинты каталога СУБД, конструктора схемы, наполнения данными, заданий и
проверки решений (исполнение `SELECT` в одноразовом Docker-контейнере, сравнение с эталоном, фиксация
попытки). Аутентификация вынесена в отдельный сервис **IdentityService** (JWT RS256 + JWKS).

**sql-module-web** — пользовательский интерфейс этого модуля. Ключевая установка: модуль самодостаточен
и не делает предположений о том, что он — корень приложения. Сейчас он работает как отдельный SPA,
а в будущем встраивается в хост-систему как компонент/виджет.

---

## 2. Назначение и границы

Модуль закрывает два рабочих контура SQL-тренажёра:
- **Преподаватель (Teacher):** каталог СУБД, визуальный конструктор схемы, наполнение датасета данными,
  создание заданий и эталонных запросов.
- **Студент (Student):** просмотр заданий, написание `SELECT`-решения в редакторе, проверка и вердикт,
  история попыток.

В модуль **не входят** (зона ответственности хост-системы / IdentityService):
- управление пользователями, регистрация сотрудников, назначение ролей (админка Identity);
- бизнес-логика проверки и хранение секретов (всё на бэкенде);
- общая навигация платформы и межмодульные сценарии.

> Экран входа в модуле есть только для **standalone-режима** — чтобы получить токен при автономной
> разработке и демонстрации. Источник токена абстрагирован (см. §5), поэтому при встраивании вход
> отдаётся хосту без переделки фич.

---

## 3. Режимы работы

| Режим | Когда | Источник токена | Навигация |
|---|---|---|---|
| **Standalone** | Сейчас: разработка, демо, защита | Встроенный экран входа → IdentityService | Собственный роутер, корень `/` |
| **Embedded** | Позже: внутри хост-системы | Токен передаёт хост (через конфиг/контекст) | Монтируется в точку хоста, base-path из конфига |

Переключение между режимами — конфигурацией, без изменения кода фич. Это главный архитектурный инвариант.

---

## 4. Роли и сценарии (UX)

| Роль | Что видит и делает |
|---|---|
| **Teacher** | Каталог СУБД (`DbmsDictionary`, `PhysicalType`, `ParameterDefinition`); **визуальный конструктор схемы** (таблицы/колонки/связи) → валидация в контейнере → сохранение; наполнение датасета (`DataRecord`/`CellValue`); темы (`Topic`), эталоны (`SqlQuery` с золотым результатом), задания (`SqlTask`) |
| **Student** | Дерево тем/заданий; экран задания: условие + SQL-редактор; отправка `SELECT` → грид результата + вердикт; история своих попыток |

Доступ к контурам ограничивается по роли из JWT (`Teacher`/`Student`). Роль `Admin`, если присутствует
в токене, в этом модуле особых экранов не открывает.

## 5. Готовность к встраиванию (embed-readiness)

Архитектурные требования, которые делают standalone-SPA встраиваемым без переписывания:

- **Единая точка монтирования.** Приложение поднимается одной функцией `mount(element, config)` —
  не завязано на конкретный DOM/`#root` и не делает глобальных сайд-эффектов при импорте.
- **Конфигурируемый base-path.** Роутер принимает базовый путь извне (в embedded — путь, выделенный хостом).
- **Pluggable источник токена.** Абстракция `TokenProvider`: в standalone — встроенный login + refresh,
  в embedded — реализация, возвращающая токен хоста. Фичи зависят только от интерфейса.
- **Самодостаточная тема.** Mantine-провайдер и стили скоупятся внутри модуля (в перспективе — изоляция
  через CSS-слои/Shadow DOM), чтобы не конфликтовать со стилями хоста.
- **Конфиг через параметры, а не через глобальный `window`.** URL API-сервисов, base-path, локаль,
  источник токена — приходят в `config`, имеют дефолты из переменных окружения для standalone.

## 6. Технологический стек

| Слой | Выбор | Назначение |
|---|---|---|
| Язык | **TypeScript** | Типобезопасность |
| Сборка | **Vite** | Dev-сервер и сборка; библиотечная сборка для embed |
| UI-фреймворк | **React** | Базовый фреймворк представления |
| Роутинг | **React Router** | Маршруты, base-path, guard-и по ролям |
| Server-state | **TanStack Query** | Кэш запросов, рефетч, статусы |
| Session-state | **Zustand** | Сессия, токен, конфиг рантайма |
| Формы/валидация | **React Hook Form + Zod** | Формы; Zod переиспользует генератор клиента |
| UI-kit | **Mantine** | Готовые компоненты, нотификации, модалки, темизация |
| Таблицы | **Mantine React Table** / **AG Grid Community** (тяжёлые гриды) | Грид результата, списки сущностей |
| SQL-редактор | **Monaco** (`@monaco-editor/react`) | Подсветка и автодополнение SQL |
| Конструктор схемы | **React Flow** (`@xyflow/react`) | Узлы-таблицы + рёбра-FK |
| Генератор API-клиента | **orval** | Типизированные TanStack Query-хуки + Zod из OpenAPI |
| JWT | `jwt-decode` + http-интерсептор | Чтение ролей, авто-refresh по 401 (standalone) |

> Версии зависимостей фиксируются на этапе скаффолдинга (актуальные стабильные мажоры).

## 7. Архитектура приложения

```
sql-module-web/
├── src/
│   ├── api/                 # СГЕНЕРИРОВАННЫЙ КОД (orval, не править руками)
│   │   ├── sqlmodule/       # хуки/типы из OpenAPI SQLModule (основной)
│   │   └── identity/        # хуки/типы из OpenAPI IdentityService (только для standalone-логина)
│   ├── app/                 # mount(), providers, router (base-path), тема, layout
│   ├── shared/              # http-клиент, TokenProvider, интерсепторы, ui-обёртки, утилиты
│   ├── session/             # источник токена и роль: standalone-login | host-token; guard-и
│   ├── features/
│   │   ├── dbms-catalog/    # СУБД, физические типы, параметры
│   │   ├── schema/          # TargetDb, конструктор схемы, данные (DataRecord/CellValue)
│   │   └── training/        # темы, эталоны (SqlQuery), задания (SqlTask), решение (SubmitAttempt), попытки
│   └── main.tsx             # standalone-входная точка (вызывает mount)
├── orval.config.ts          # цели генерации: sqlmodule (+ identity для standalone)
├── CONCEPT.md
├── ROADMAP.md
└── TECHNICAL_REQUIREMENTS.md
```

Принципы:
- **Server-state vs session-state.** Данные бэкенда — через TanStack Query; токен/роль/конфиг — в Zustand.
- **Сгенерированный слой неприкосновенен.** `src/api/*` — целиком из orval; бизнес-хуки и обёртки — в `features/*`.
- **Фича = вертикальный срез** (экран + хуки данных + формы + типы), зеркалит вертикальные слайсы бэкенда.
- **`session/` — единственное место, знающее, откуда взялся токен.** Фичи работают с токеном через интерфейс.

## 8. Интеграция с бэкендом

- **Основной сервис — SQLModule** (каталог, схема, данные, задания, попытки).
- **IdentityService — только для standalone-логина** (получить токен; в embedded не используется).
- Клиент генерируется orval из OpenAPI-документов; контрактные DTO (`CreateSchemaRequest`,
  `SubmitAttemptResponse`, `QueryResultSet` и т.д.) приезжают на фронт автоматически.
- Стыковка конструктора: бэкендный `CreateSchemaCommand` оперирует `TempId` для колонок/связей —
  узлы и рёбра React Flow несут `TempId`, форма собирает ровно тот `CreateSchemaRequest`, что ждёт сервер.

## 9. Методология разработки (агентский подход)

Разработка ведётся агентски: владелец продукта ставит задачи, ассистент готовит **промты для
агентов-разработчиков**, артефакты создаются и итеративно уточняются. Принцип «**сначала концепт**»:
фича сперва описывается в `CONCEPT.md`/`TECHNICAL_REQUIREMENTS.md`, затем превращается в промт с чётким контекстом
(эндпоинты orval, типы, компоненты Mantine, критерии готовности), затем реализуется и проверяется.
Документы — единый источник истины для промтов.
