# SQL Module Web — концепция

Актуализировано: 2026-09-12.

## 1. Назначение

SQLModule — практический модуль платформы Scoodle для подготовки и автоматической
проверки заданий по SQL. `sql-module-web` предоставляет три ролевых контура:

- `Admin` — пользователи IdentityService, роли, блокировки, аудит и справочники;
- `Teacher` — темы, учебные базы, схемы, данные, задания, эталоны и попытки;
- `Student` — опубликованные задания, SQL-редактор, результат и история попыток.

Модуль работает автономно и через переход с образовательной платформы. Автономный
режим является постоянной возможностью, а не временной заглушкой.

## 2. Границы ответственности

Frontend отвечает за ролевую навигацию, формы, отображение схемы и результатов,
управление standalone/handoff-сессиями и вызов типизированных API-клиентов.

Решение о доступе, выполнение SQL, сравнение с эталоном, идемпотентность, выпуск
токенов и начисление оценки остаются ответственностью IdentityService, SQL Module
API и Education. Frontend guard улучшает UX, но не является защитным периметром.

## 3. Режимы работы

| Режим | Вход | Хранение токена | Особенности |
|---|---|---|---|
| Standalone | Login через IdentityService | Постоянная сессия, access/refresh lifecycle | Не зависит от Education и Kafka |
| Student handoff | `/launch#access_token=...` | `sessionStorage`, без refresh | `ModuleSession`, canonical task и return URL от backend |
| Teacher handoff | `/teacher/launch#access_token=...` | `sessionStorage`, без refresh | `Teacher`/`Admin`, без `ModuleSession` и `session_id` |

Fragment удаляется до сетевых запросов. Handoff не перезаписывает standalone.
Logout, 401 и ошибка запуска очищают временный provider.

## 4. Пользовательские контуры

### 4.1. Преподаватель

Преподаватель управляет темами, учебными базами, схемами, исходными данными,
заданиями, эталонами и попытками. Тип колонки выбирается только из каталога
физических типов выбранной СУБД; порядок таблиц и колонок меняется drag-and-drop.

Схема задаётся визуально или DDL-скриптом. Validate и Apply используют единый
backend-анализ. Безопасные изменения применяются точечно, запрещённые возвращают
violations с `path`, `code`, `severity` и `affectedRows`. ER-диаграмма показывает
структуру базы.

Задание и эталон связаны один к одному. Эталон не выбирается из общего списка и не
имеет отдельного пользовательского названия; он редактируется в карточке задания.

### 4.2. Студент

Студент видит только опубликованный контент через student-safe API. Карточка не
раскрывает эталонный SQL, эталонные строки и служебные поля.

Решение вводится в Monaco, хранится как локальный черновик и отправляется с UUID
`Idempotency-Key`. После неопределённой сетевой ошибки ключ сохраняется для
безопасного повтора. Backend возвращает вердикт, длительность и ограниченный
snapshot фактического результата с nullable-ячейками. История ограничена текущим
студентом.

### 4.3. Администратор

Администратор управляет пользователями IdentityService, ролями, блокировками,
аудитом и справочником СУБД. `Admin` также допускается в авторинг политикой
`ContentAuthor`; Teacher и Student не получают административные маршруты.

## 5. Интеграция с платформой

### 5.1. Студенческая сессия

Education создаёт `ModuleSession`, а JWT содержит audience `sql-module-api` и
`session_id`. `sessions/current` возвращает доверенные `taskId`, `returnUrl` и
`expiresAt`. До sandbox backend проверяет владельца, задачу, состояние и срок
сессии. Первая правильная попытка создаёт оценку 100. Событие публикуется через
Kafka outbox, оценка передаётся в Education по HTTP, затем frontend возвращает
студента по доверенному `returnUrl`.

### 5.2. Авторинг преподавателя

Платформа открывает `/teacher/launch` с короткоживущим JWT роли `Teacher` или
`Admin`. SQL-модуль не создаёт student launch context, не вызывает
`sessions/current` и не требует `session_id`.

## 6. Технологический стек

| Слой | Технология | Назначение |
|---|---|---|
| UI | React 19, TypeScript | Типобезопасный интерфейс |
| Сборка | Vite | Dev/build и code splitting |
| Компоненты | Mantine | Формы, таблицы, модальные окна |
| Роутинг | React Router | Base path, launch routes и guards |
| Server state | TanStack Query | Кэш, пагинация и инвалидация |
| Session state | Zustand, TokenProvider | Standalone и handoff lifecycle |
| Формы | React Hook Form, Zod | Формы и клиентская валидация |
| SQL | Monaco Editor | Решение и эталон |
| ER | React Flow, ELK | Граф и автоматическая раскладка |
| API | Orval | Клиенты из Swagger |

## 7. Архитектура frontend

```text
src/
  app/        providers, runtime config, router, layout, mount
  pages/      страницы верхнего уровня
  features/   пользовательские действия и формы
  entities/   доменные модели представления
  shared/     HTTP, UI, утилиты и типы
  session/    TokenProvider, login, launch context и guards
  api/        generated Orval clients
```

Правила:

- API state хранится в TanStack Query, session state — в Zustand/provider;
- `src/api/*` не редактируется вручную;
- URL сервисов и `basePath` приходят из runtime config;
- фичи не читают токены напрямую из storage;
- тяжёлые маршруты и редакторы загружаются лениво;
- повторяемые компоненты размещаются в `shared/ui`.

## 8. Модель учебной базы

Основная PostgreSQL-база хранит доменные сущности и метаданные. Пользовательский
SQL выполняется только в изолированной временной среде с ограничениями операций,
времени и размера результата. Метасхема позволяет описывать учебные таблицы без
миграции основной базы. DDL и визуальная форма сводятся к одному backend-контракту.

## 9. Безопасность

- токены не попадают в query string, логи и пользовательские сообщения;
- launch fragment очищается немедленно;
- handoff token живёт только во вкладке и не имеет refresh token;
- student endpoints применяют server-side publication и owner scope;
- эталон и raw sandbox errors не возвращаются студенту;
- идемпотентность защищает повторную отправку;
- разрушительные schema changes отклоняются до применения;
- CSP и `Referrer-Policy` задаются приложением и reverse proxy.

## 10. Вторая итерация

Вторая итерация включает production smoke, масштабирование списков, code splitting,
интерактивную ER-диаграмму, schema-aware Monaco, устойчивость Student UX и
минимальную автоматизированную регрессию.

Составная проверка, скрытая read-only база, веса, попытки и финализация подробно
зафиксированы в `docs/SECOND_ITERATION_TASK_VALIDATION_CONCEPT.md`.

Назначения, дедлайны, аналитика, импорт/экспорт и асинхронная отмена попытки требуют
отдельных продуктовых решений.
